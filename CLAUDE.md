# Brawlchemist

Brawlhalla stats platform (dpm.lol / op.gg style). Next.js 16 App Router, React 19, Tailwind v4, Drizzle + postgres-js on Supabase (free tier), deployed on Vercel.

## Commands

- Dev: `npx next dev --turbopack -p 3137` (background) — poll with Invoke-WebRequest until 200
- Typecheck: `npx tsc --noEmit` (run before every commit)
- **`drizzle-kit push` DOES NOT PROMPT** (`--strict` is opt-in) and reconciles the DB *down to* `lib/db/schema.ts` — it DROPS any index it can't see there. It silently removed all four perf indexes once, taking username search from ~400ms back to 95s. Every index must be declared in the schema file, never only in SQL. There is no read-only "check" mode; `drizzle-kit pull` is the only safe way to inspect.
- Schema: `npm run db:push` (drizzle-kit push straight to prod Supabase — NO migration files; run deliberately), `npm run db:studio`
- Index/DDL + one-off maintenance: `db/perf-indexes.sql`, `db/reclaim-space.sql` and `db/rls-policies.sql` (re-run the last one after any `drizzle-kit push` — see Security), pasted into the Supabase SQL editor. Not runnable through DATABASE_URL — Supavisor caps statements at 2min and silently corrupts `CREATE INDEX CONCURRENTLY` (returns success, leaves `indisvalid = false`)
- **An `ALTER TABLE players` will not get its lock on the first try**, and the error it fails with ("canceling statement due to statement timeout") describes the timeout, not the cause. Serverless instances leave transactions open on `players` — `state = active`, `wait_event = ClientRead`, `xact_start` 30+ minutes ago — holding AccessShareLock forever because the client that started them is long gone. ADD COLUMN needs ACCESS EXCLUSIVE and queues behind them, and while it queues it blocks every reader too. The recipe: connect to the **session** pooler (:5432, the only one where `SET` sticks), `SET lock_timeout = '3s'` so a failed attempt fails fast instead of stalling the site, `pg_terminate_backend` the ClientRead zombies older than 5 minutes, then retry. Adding a nullable column with no default is metadata-only, so it does not rewrite the 200MB table once the lock is granted
- PowerShell 5.1 quirk: commit messages / PR bodies containing `"` get mangled as inline args — ALWAYS `git commit -F <file>` and `gh pr create --body-file <file>`
- `gh pr create` sometimes claims the branch isn't pushed — retry with explicit `--head <branch>`

## Cardinal constraints (override convenience every time)

1. **Brawlhalla API: 180 req/15min, fully budgeted.** New features must NOT add API calls. Piggyback existing fetch paths; read from our own DB/caches. `upsertPlayerRanked()` (lib/sync/players.ts) is the single chokepoint where every fresh `/ranked` payload lands (profile views + crons) — snapshot-style features hook there.
2. **Supabase free tier: egress matters — 5GB/mo, and it has been blown 3x.** Never `SELECT *` on tables with jsonb. Select narrow columns; `getPlayersByIds(ids, { includeRankedJson: false })` for anything that doesn't read legends. The two offenders found by `pg_stat_statements` (order by `rows` desc — it's the best egress proxy available): sync-live reading the whole `live_ranked` snapshot every 5min (180M rows ≈ 16GB) and the profile page pulling `ranked_json` (~6.3KB/row) just to test freshness across 1.2M views (≈7.6GB). **A cron that diffs a snapshot must read only the ids it is about to reconcile, and only the columns it compares.**
3. **Crawlers never spend Brawlhalla API budget.** 53% of profile views are bots (Bingbot alone 42%), and each used to trigger /ranked + /stats + /guild — three calls against the 180/15min budget — leaving real visitors on the 429 fallback. `isCrawler()` (lib/bots.ts) routes them to stored data at any age; `loadRanked` returns `source: "db-crawler"` and the page skips every upstream call. Separate from middleware's `BLOCKED_BOTS` (hard 403 for AI/SEO scrapers) — these are crawlers we WANT indexing us.
4. **Supabase free tier: 500MB database size.** Storage is as scarce as egress and the project has been over. Anything written per page view needs a retention window AND a small row — `fetch_log` hit 362MB (59% of quota) because it stored a ~125-byte User-Agent on every one of ~15k rows/day forever; it now stores a ~10-byte `clientLabel()` with a 14-day prune. Remember DELETE does not shrink the file on disk — only `VACUUM FULL` moves Supabase's size metric (see `db/reclaim-space.sql`). Next lever if it grows again is `players` (200MB, all `ranked_json`): evict the blob for cold, non-Valhallan players rather than touching the aggregation pool.
5. **Everything fails open — OUTSIDE the cache, never inside.** Enrichment lookups (profiles map, players cache, CM, esports) degrade to plain rendering rather than taking down a page. But a `catch` *inside* `unstable_cache` turns that virtue into an outage: the empty value is a successful return, so the cache stores it and serves it as fact for the whole revalidate window, and every failed refresh renews it. On 2026-09-18 one `CONNECT_TIMEOUT` to the pooler emptied `getProfilesObject` (1h window) and for an hour **no pro had a handle anywhere on the site** — no linked-account badge, no flair, no favourite skin, no esports title — while all four of its reads answered in under two seconds when measured. So: **a cached function must throw**; a thrown error is not cached, and the first success repairs everything. `failOpen` (lib/sync/fail-open.ts) is the wrapper, and it carries a 10s per-reader cooldown so "don't cache the failure" doesn't become "retry on every request" against a database that is actually down. Applies to `getProfilesObject`, `getFlairObject`, `getCustomization`, `getFlairCatalogueCached`, `getFlairGrantsObject`, `getSmurfIdList`, `getFavoriteIds` — all six had it.

   **A sub-read inside a cached function is the same bug wearing a disguise, and it shipped.** `getProfilesObject` rethrows on its main read — correct — but its two side reads, flair grants and esports titles, each caught their own error and returned an empty Map. The stated reason was deployment ordering: a table not yet pushed should cost a badge, not every profile. Right about the deploy, wrong about everything else — an empty Map is a *successful* return, so `unstable_cache` stored it and served it as fact for the whole window. Measured on 2026-09-20: **every esports title on the site was missing** — no gold chips on any profile, and no World Champion flair for the three players who hold one — because that read failed once during a pooler jam. The players still had their titles in Postgres the whole time. Both sub-reads now rethrow, so the entry is never written and `failOpen` repairs on the first success.

   Still carrying the same shape, each without a `failOpen` wrapper to land in, so fixing them means adding one first: `getCombosObject` (lib/sync/true-combos.ts, caches `{}`), `fetchGuildLeaderboard` (lib/sync/guilds.ts, caches `[]`), `getViewerDefaultRegion` (lib/sync/viewer-prefs.ts, caches `null`).
6. **Never put a `players` full-table scan on a render path.** `players` is ~90k rows / ~200MB, almost all of it `ranked_json` in TOAST. Any query that evaluates a `ranked_json` expression in a WHERE/ORDER BY across the table detoasts all of it. Order search/list queries by the denormalised `rating` column (see #8), not by a jsonb expression.

   **The Valhallan aggregations broke this rule for months, in the one place this file called legitimate.** Every one of them filtered `(ranked_json->>'rating')::int >= 2300` — re-deriving from the blob the value `players.rating` is denormalised to hold — so the filter meant to narrow 90k rows to 2k read all 90k first. That is why they "legitimately take 25–95s": they never had to. Swapping to the indexed column, with output proved identical (2,043 rows both ways, zero disagreement in either direction):

   | | via `ranked_json` | via `rating` | |
   |---|---|---|---|
   | sample count | 9,613ms | 571ms | 17× |
   | legend stats, global | 16,223ms | 2,017ms | 8× |
   | legend stats, US-E | 16,766ms | 531ms | **31×** |
   | mainer counts | 31,072ms | 570ms | **54×** |
   | top mainers | 13,535ms | 704ms | 19× |

   **The aggregations are no longer on the render path at all.** `valhallan_stats` holds every variant as a jsonb payload keyed `${kind}:${region}:${method}`, the daily cron writes all 60 (measured: 29-60s for the set, 96KB total), and the readers do one primary-key lookup and return **empty** when a row is missing. A page may be stale; it must not be slow. `?statsOnly=1` on the cron recomputes them without walking the leaderboard API, because "recompute the meta" and "refresh the pool" should not cost the same 180/15min budget. `minGames` is derived from (method, hasRegion) rather than enumerated, which is what keeps the homepage's `{popular, ALL, 100}` and /meta-picks' default the *same* row; mainers are stored once at depth 5 and sliced, since the top three are a prefix of the top five.

   `valhallanRatingClause()` is now the single place that asks the question, so the next aggregation cannot quietly reintroduce the slow form. `regionClause` still reads `ranked_json->>'region'` and costs nothing, because the index narrows first and only those 2,043 rows are detoasted — which is why the *regional* case is the fastest of the three. They stay behind `unstable_cache` (`VALHALLAN_STATS_TAG`, 6h): call the exported `get*`, never `compute*`. **A cache miss still computes on a user's request**, and the key includes `{region, method, minGames}`, so it is ~22 entries that miss independently rather than one that warms once — which is the remaining reason to move this into the cron and have readers only SELECT.

   `lib/sync/admin-stats.ts` used to do a real full scan — its CASE read `ranked_json->>'tier'`, and this note called the detoast unavoidable. It was not: the tier bands are a function of `rating` everywhere else on the site (`TIER_FLOOR`), so bucketing the indexed column asks the same question as a parallel index-only scan. Measured 29.1s → 1.35s, and the old form sat exactly at the role's 30s `statement_timeout`, which is why the System tab was "inaccessible": it crawled or failed open after half a minute, on every visit, uncached. It is behind `unstable_cache` (10 min) + `failOpen` now. What it gave up is telling name-only harvest rows from the unranked, because that needs `ranked_json IS NULL` and that predicate alone is a 9.3s sequential scan; both are "no rating on the row". `lib/sync/otps.ts` looks similar and is not — it filters on the indexed `top_legend_id` (1.5s) and only projects rating.

   **A rank nobody can reproduce is not a rank.** `computeTopValhallanMainers` ordered its windows by rating alone, so players on the same rating got an arbitrary order — swapping the filter appeared to change 70 of 209 rows when the row set was provably identical, and two players swapped in and out of a `rn <= 3` cut. Both windows now break ties on `brawlhalla_id`, which made the before/after exactly identical and the query repeatable.
7. **The Brawlhalla API double-encodes UTF-8.** It serves `application/json` but builds its JSON escapes from already-UTF-8 bytes treated as Latin-1, so "Areté" arrives as "AretÃ©". Not a font bug — no display change fixes it. `repairJson()` (lib/text.ts) is deliberately conservative (telltale byte pattern + exact round-trip check) because an eager version corrupts legitimately non-ASCII names; 3,313 stored usernames needed repair and 16 fail the round-trip check (names the API truncated mid-codepoint) and are left alone. **It must be applied on BOTH edges, not just the API one.** `apiFetch` cleans payloads arriving fresh from upstream, but `players.ranked_json` still holds blobs written before that landed, and the profile page serves the stored blob whenever the row is fresh (6h idle window), the visitor is a crawler, or upstream 429s — i.e. the mangled name survived on exactly the paths that skip the API. So `getPlayerRankedJson` and `getPlayersByIds` repair on the way out too. `live_ranked.players` needs no backfill: the cron rewrites it every 5 min through `apiFetch`. Repairing the username column alone is NOT enough — the profile page renders `ranked_json.name`, not `players.username`.
8. **Ordering must use an indexed scalar, bare.** `players.rating` is denormalised out of `ranked_json` by `upsertPlayerRanked` for exactly this. Do NOT order by a `ranked_json` expression (detoasts ~200MB, measured 95s) and do NOT wrap the column in `coalesce()` — that alone made `players_rating_idx` unusable and a two-character search went 0.4s → 15s. `ladder_rating` and `ladder_region` are both dead columns: only the search-index harvest writes them and nothing calls that harvest (measured: 0 non-null `ladder_region` out of 95,635 rows, while 94,928 have one in `ranked_json`). Anything needing a region must coalesce — `getPlayersByIds(ids, { withRegion: true })` does, opt-in because it detoasts per row. The bare column silently rendered no region pill on /favorites for as long as that page has existed.

   **An index only serves an ORDER BY whose null ordering matches it.** `players_top_legend_rating_idx` is `(top_legend_id, rating DESC NULLS LAST)`; querying it with a bare `ORDER BY rating DESC` (which means NULLS FIRST) drops the planner onto a bitmap heap scan — measured 1.9s vs 0.05ms for the same three rows. Same family of trap as wrapping the column in `coalesce()`.
9. **Supavisor pool is small and shared.** postgres-js defaults to `max: 10` with no idle timeout, so each serverless instance parks ten pooler slots forever; `lib/db/index.ts` caps it. The transaction pooler (:6543) silently IGNORES a `statement_timeout` startup param and ignores `SET` — for DDL or anything needing a longer/shorter timeout, connect to the session pooler (:5432) where `SET statement_timeout` sticks.

   **`statement_timeout` for `postgres` is 30s.** It had none, inheriting the 2min default, and that is how one query held a pooler slot while every page queued behind it — the cascade that produced 289 function timeouts and 176 affected users in a day. 30s is ~15x the heaviest legitimate query now that the aggregations run in ~2s, and above admin-stats' 16s full scan so nothing that worked before starts failing. It could not have been set while those aggregations took 25-95s, which is exactly what the note above used to say: **fix the query first, then the timeout becomes available.** Applies to backends started after the change; existing pooled ones keep 2min until Supavisor recycles them, so it cannot be observed immediately from a pooled connection.

   **But `ALTER ROLE` DOES reach backends through both poolers.** A role default lives in `pg_db_role_setting` and is applied when a *backend* starts, which is upstream of anything Supavisor drops — so it is the one way to set a real per-session default for the app. Measured: after `ALTER ROLE postgres SET idle_in_transaction_session_timeout = '60s'`, a newly-created backend reached through :6543 reports `1min` while pre-existing pooled backends still report `0` until Supavisor recycles them. We connect as `postgres`, which (unlike `authenticated`/`anon`, capped at 8s/3s) had **no** overrides at all — it inherited `statement_timeout = 2min` and `idle_in_transaction_session_timeout = 0`. Do not tighten `statement_timeout` below ~2min: the sanctioned Valhallan aggregations legitimately take 25–95s (measured 26.7s for a full `ranked_json` scan today).

## Security

- **Supabase is an auth provider here, and nothing else — but it published every table anyway.** PostgREST exposes everything in `public`, and Supabase grants `anon`/`authenticated` privileges on new tables *by default*. The anon key is the publishable key, which ships in the browser bundle, so it is public by construction. Measured on 2026-09-20 with nothing but that key: `GET /rest/v1/app_users` returned **every user's email, plan and account_role**; `profile_claims` returned `challenge`, the answer to the ELO quiz that proves profile ownership; `players` returned the whole ~300MB table; `PATCH /rest/v1/profiles` returned 200 and `DELETE /rest/v1/fetch_log` returned 204. Writes were the worst of it: `app_users.account_role` is what `isAdmin()` reads, so **the admin panel was one PATCH away for any visitor**. `db/rls-policies.sql` closes it — REVOKE on tables/sequences/routines, REVOKE USAGE on the schema, `ALTER DEFAULT PRIVILEGES` so the next `drizzle-kit push` cannot re-grant, and RLS ENABLE on all 18 tables. Verified after: the same requests return 401 `42501`.
  - **ENABLE, never FORCE.** The app connects as `postgres`, which owns these tables and bypasses RLS; that is precisely why this was shippable without touching application code. `FORCE ROW LEVEL SECURITY` would apply the policies to the owner and take the site down.
  - **Privileges are the layer that silently comes back**, which is why revoking alone is not the fix. Supabase's default privileges hand each newly created table to `anon`, and this project ships schema with `drizzle-kit push` and no migration files — so a new table is a new hole unless the default-privileges rules are in place. Re-run the two verification queries at the bottom of that file after any push.
  - **Policies are written but inert**, deliberately. Row rules exist for the three tables that have a real owner (`app_users`, `profile_claims`, `user_customizations`) so the ownership model lives in the database and a future client-side feature starts from a correct filter. Everything else gets no policy, which means denied. Do **not** be tempted to hand `anon` a blanket SELECT on the "public" tables: `players` is ~300MB and a public SELECT on it is an unauthenticated, uncached bulk export against a 5GB/month quota that has already been blown three times, and `profiles.user_id` is the link between a player and an account, which the site deliberately never publishes.
  - Real enforcement of ownership stays where it already was: `authedUserId()` plus a `profiles.userId` check at the Server Action boundary. RLS here is defence in depth, not the mechanism.

## Data architecture

- `players` — PK brawlhalla_id; `ranked_json` (full GetPlayerRanked, drift-safe jsonb), `top_legend_id` (pre-computed main), ladder snapshot scalars, guild fields, `last_synced`
- `profiles` — admin-curated competitors (handle, favorite skin); `getProfilesMap()` cached 300s, tag "profiles"
- **"Verified" is a set of kinds, not a ladder.** It began as `is_pro`, a boolean that could only say "we vouch for this person"; then as `pro_tier`, an ordered ladder of competitive standing. The ladder stopped fitting when the question became *who do we vouch for* rather than *how good are they* — a Content Creator is not above or below a Pro Player, and a Developer is not a weaker Hall of Famer. `profiles.pro_tier` now holds a **kind**: `top` (gold) | `pro` (turquoise) | `hall-of-famer` (silver) | `content-creator` (Twitch purple) | `developer` (pink) | `power-ranked` (grey) | `none`, read through `parseVerifiedKind` (lib/profile/verified.ts) so an id we no longer ship degrades to no badge rather than to a claim nobody can account for. The point of the whole feature is that a verified player's **handle replaces their in-game name everywhere**; the badge is how you know why.
  - **`order` is display precedence, not rank.** It decides which badge gets the slot when only one fits (a 2v2 podium carries one mark for the pair — `primaryVerifiedKind`) and what order the picker lists. Nothing may read it as a ranking, because these kinds are not comparable.
  - **Every comparison is a named flag.** `isVerified` — gets a badge and a handle. `isCompetitive` — belongs on a board that ranks ladder rating, which is what keeps a streamer off the Pros leaderboard and out of the esports linking screen (`competitiveClause()` is its SQL twin). `kindCanEditLinks` — may put an outbound URL on a public page; everyone we vouch for can, Power Ranked cannot, because "we know of this competitor" is not the same as vouching for where they point their audience. Inserting a kind must never silently hand it a capability nobody granted, which is the trap `ROLES.admin` is written around.
  - **Curated, never derived.** There is no fact on a player record that says "content creator", and "places well consistently" is a judgement about a career rather than a defensible threshold. /admin shows the evidence it holds beside the picker — titles, events, best finish, which are only meaningful for the competitive kinds — and a human asserts.
  - **The stored names did not change, and that is deliberate.** The column is still `pro_tier` and the flair rule token is still `pro-tier`: `drizzle-kit push` has no rename, and `parseFlairRule` degrades anything unrecognised to `manual`, so renaming the rule would silently demote the Grand Champion flair between the deploy and the data edit. The schema maps `verifiedKind: text("pro_tier")`. Same two-step `esportsTitles` is in.
  - **The kind is erased into `PlayerPreview.verified`, and that is why the rename stayed small.** `toPreview` sets `verified: { handle, kind }` iff the kind is verified, so the ~35 surfaces that only ask "is this someone we vouch for" keep testing `preview.verified` unchanged; only the badge reads `.kind`. Every badge site goes through `previewKind()`. **`kind` is optional and the older `tier` is still read**, because this object is cached for an hour: the deploy that renames the field has live entries holding the old key, and `kindFromVerified` reads `kind` then `tier` then falls back to `pro`, so nobody loses their check while an entry ages out. Both shims are droppable an hour after that deploy.
  - **`VerifiedMark` takes a required `kind` and owns its own fallback** — `none` renders nothing. Same contract as `RankHelm` and `LegendChip`: never guard a call site with `{kind && <VerifiedMark …>}`. Required rather than defaulted so adding a kind cannot leave a surface silently drawing the old check.
  - **SQL asks the question in one place**: `lib/sync/verified-sql.ts` (`verifiedClause()`, `competitiveClause()`, `verifiedOrderExpr`), the same reason `valhallanRatingClause()` exists. A bare `desc(pro_tier)` sorts **lexically**, which looks like a working sort and is not one. `competitiveClause()` builds its `IN` list from the catalogue — **and parenthesises it**: `sql.join` emits `$1, $2, $3` with no brackets, which is a syntax error at runtime that no type check catches. Only executing it does.
  - `is_pro` **stays declared and written** for one deploy (derived in `upsertProfile`, nowhere else, so it cannot drift). Every SQL reader uses `coalesce(pro_tier, case when is_pro then 'pro' else 'none' end)`. Droppable next deploy.
- `user_customizations` — what an owner chooses about their own profile: banner, flair, favourite legends, links. **Every field is a choice from a list we control.** There was a freeform bio; it was the only thing on the site whose contents nobody could check, and it is gone — including the `ProfileCustomization` card, which held nothing else. All customization now renders in the profile card (header), never in a section below it
- **A profile link must point at the site its glyph names.** `SOCIAL_HOSTS` (lib/profile/social.ts) is the allow-list and `isAllowedSocialUrl` the check; matching is exact-host or true subdomain, never `includes`, so `evil-x.com` and `x.com.evil.net` are both rejected while `www.` and `m.` are not. There was a sixth kind, `website`, that took any https URL — one profile was using it to link a porn site from a page with our name on it. Removing the kind alone would have fixed nothing, because nothing checked the host either: the same URL filed under "twitch" would have drawn the Twitch glyph and linked straight to it. **The check runs on the way OUT as well as in** (`parseSocialLinks`), which is what let the rule be tightened with no migration — a row written before it existed simply stops being returned, so it stops rendering the deploy it ships in rather than waiting on a cleanup. Same both-edges shape as `repairJson`. The panel runs the same check so a rejected URL is named rather than silently dropped on save
- **Only the links are gated, and the gate cannot destroy data.** A favourite legend is a pick from a fixed roster — nothing to moderate, nobody to vet — so it is open to everyone; links put an outbound URL on a public page, so they stay with verified pros and developers. `saveProfileFieldsAction` **carries the stored links through** rather than writing `[]` when the caller isn't entitled: refusing the whole save would lose their legends too, and writing empty would let a failed `getProfile` read, or a pro whose verification lapsed, silently delete links they had already saved. Not entitled means "cannot change these", never "these are now empty"
- **Every customizer change is local until Save, and every one of them previews on the card above.** The two halves go together and neither works alone: holding changes locally is what makes Cancel possible, and putting the pending value on the header is what makes a banner, a skin or a main judgeable at all — a 32px swatch tells you nothing. `ProfilePreviewProvider` carries banner, flair, skin and legends; `PreviewBannerWash`, `PreviewFlair`, `PreviewSkin` and `ProfileIdentityRow` read it and fall back to the server value, and every one returns the server value untouched when there is no provider. Two traps it is built around: the skin slot is **tri-state** (`undefined` = nothing pending, `null` = pending-none), because collapsing them makes *clearing* your skin the one change the preview cannot show; and the preview carries legends as resolved `{name, slug}`, not roster ids, because whoever holds the ids needs `LEGEND_ROSTER` to draw them and putting that in the identity row ships all seventy legends to every visitor for a preview only the owner can trigger
- **Saving the customizer does a real document load**, not `router.refresh()` + `router.push()`. Those go through the client router, which serves the profile out of its own RSC cache for an entry it already had, so a save could land and the page you arrived back on still showed the old skin. The reload is deferred by ~0.9s (2.6s when an achievement fired) because a document load tears down the toast layer — and the unlock toast is the one thing on the page that exists only for that moment, announced at the click that earned it and never re-derived
- `app_users` — one row per Supabase identity. **Two independent account axes, never one enum** (lib/auth/account.ts owns both lists and everything they grant): `account_role` = permission (`developer` | `partner` | `user`), `plan` = subscription (`free` | `supporter` | `founder`). Split because a Partner can also be a Founder, and because a lapsed card must never be able to revoke admin. "Linked User" is a **sixth level that is derived, not stored** — a `user` who owns a `profiles.userId`; storing it would drift, since that link moves in three places. Reads go through `parseRole`/`parsePlan`, so unknown values degrade to `user`/`free` (which is why the legacy `plan='premium'` needed no backfill)
- **A page-level `redirect()` is not an auth gate on a route with a `loading.tsx`.** `redirect()` only becomes a 307 while the response has not started; a streamed route sends its shell first, so the redirect degrades to a client-side navigation and the route answers **200 with a shell** to anything without JavaScript. /favorites had a loading.tsx and /account did not, which is the whole reason one of them gated and the other silently didn't. Signed-in-only routes are therefore listed in `SIGNED_IN_ONLY` in `middleware.ts`, which decides before a byte is rendered; `updateSession` hands back `signedIn` for free, since the cookie refresh already reads the claims. The in-page checks stay as defence in depth for anything not on that list.
- **A server component importing a plain value out of a `"use client"` module gets a client reference, not the value** — and it does not throw. The proxy's properties read as `undefined`, `cn()` drops them, and you get markup missing exactly the classes you thought you shared. /meta-picks shipped this for a day: the table's column widths were exported from `components/site/meta-table.tsx`, the server-rendered detail panel read `META_COL.stat` off the proxy, and every width silently vanished — measured 57px and 44px where 76 and 84 were declared, with the numbers a few pixels off their headings. Constants shared across the boundary live in a plain module (`lib/meta-columns.ts`); only components should be imported from a client file.
- **`public/assets` is foldered, and two things pin a file's path.** Art lives under `avatars/`, `badges/`, `flairs/`, `gems/`, `legends/`, `media/`, `ranks/` (helms, rank icons and banners), `regions/`, `stances/`, `weapons/`. What stays loose at the root is the set whose paths are **stored in Postgres** — `flairs.src` and `profiles.favorite_skin.src` — because moving one 404s in production until the row is updated, and the deploy and the data edit cannot land at the same instant. Moving those needs a two-step: ship a copy at the new path, update the rows, delete the old. **Before deleting anything as "unused", remember paths are also built dynamically**: `/assets/ranks/Banner_Rank_${tier}.webp` and `/assets/legends/${slug}.png` never appear as whole strings in the source, so a naive grep reports all seven rank banners and every legend portrait as orphans. An audit that does not expand those two patterns will happily delete the profile header's artwork.
- **Admin access is a role, not a password.** `isAdmin()` = signed-in account with `account_role='developer'`, OR an email in `ADMIN_BOOTSTRAP_EMAILS` (env-only, nothing in the app can write it — it's the bootstrap, since Developer can only be granted from inside the panel, and the way back in after a mis-demotion). - **`earnings` is the fifth flair rule, and Grand Champion is the reason.** `rule: "earnings"` + `rule_value: "50000"` fires when career prize money is **at least** that many whole dollars. A threshold rather than an exact match, unlike `pro-tier`, because money is a quantity: raising the bar later narrows the badge instead of silently re-pointing it at a different group. Two guards, and the second is the one that matters — a missing threshold and a threshold of **zero** both fire for nobody, because zero would hand the badge to every player we have ever looked up. Measured after the first sync: 100 of 176 profiles known to brawltools, **15 clear $50,000**, highest $258,984 — and the overlap with Top Player is 8, with 7 qualifying on money alone and 2 Top Players not reaching it, which is the separation this rule exists to draw.
  - **`profiles.earnings` is stored, not fetched per render**, and that is forced by where flair renders: fifteen surfaces read the cached profiles map, so a fact only the profile page holds would give a badge that appears there and nowhere else. `scripts/sync-earnings.mjs` fills it from brawltools (keyless, **no Brawlhalla budget**). **Null is not zero**: null means we never looked and the rule declines rather than guessing, while 0 is a fact about someone who has won nothing.

Same hazard the `achievement` token is kept for, arrived at from the other direction.
- **A flair rule is code; `pro-tier` is the fourth of them.** `rule: "pro-tier"` + `rule_value: "<kind id>"` fires when a player's verified kind is **exactly** that one — Grand Champion is `pro-tier:top`, so it reaches the five Top Players and nobody else. Exact, never "this tier or better": a threshold would silently widen the moment a tier is inserted between two others, which is the same trap `ROLES.admin` and `canEditLinks` are named flags to avoid. Two guards matter and both are load-bearing — a value that is not a tier we ship, and the value `none`, each fire for **nobody**, because without the second a typo would parse to `none` and hand the badge to every uncurated player on the site (almost everyone), exactly as an empty `achievement` needle would. It is in `SELECTABLE_FLAIR_RULES` alongside `achievement` and `manual`: unlike `claimed` and `developer` it is earned, rare, and genuinely a choice — a player who holds it may prefer to fly something else. **Sort 30 puts it below World Champion on purpose**, so an editorial badge of ours never outranks an actual championship; the consequence is that the auto-pick rarely lands on it (7 world champions against 5 Top Players, heavily overlapping), so in practice it is a badge you *choose* rather than one you are given.
- **`flairContextFrom` reads the standing from two shapes**, because a `PlayerPreview` carries it inside `verified` and a hand-built member object carries it flat. Both are resolved in that one function rather than at fifteen call sites — it takes a *structural* type, so an object missing the field is still assignable and quietly reads as "no standing", which is the trap this file already records for the `esportsTitles` rename.
- **No linked account, no flair — any badge, any surface.** `earnedFlairIds` returns an empty list when `ctx.claimed` is false, which gates every path because that is the one function both `resolveFlairs` (for `FlairMark`) and the profile page's `earned` list (for `PreviewFlair`) resolve through. A flair is something a person chose to fly and someone who never signed up has chosen nothing, so deriving one for them puts our decoration on a stranger's name. A crumb written before this shows no flair until that player is visited again, which is honest rather than broken.

- **`BUILTIN_FLAIRS` is a fallback, not a seed.** It is consulted only when the `flairs` read comes back empty or throws, and that table has been seeded since the admin panel landed — so adding a badge to the array alone puts it in the code and nowhere anyone can see. A new flair needs its row too (Early Tester was added that way: `manual` rule, because there is no fact on a player record that says "was here early").
- `flairs` + `flair_grants` — the badge catalogue, curated at /admin, and the ledger for hand-awarded ones. **The catalogue is data; entitlement is code.** `flairs.rule` is a closed allow-list (`developer` | `claimed` | `achievement` + `rule_value` | `manual`) read through `parseFlairRule` — an operator picks which rule a badge uses and cannot author a new one, because "has this player earned it" is only answerable against the player record. `manual` is what makes "create a flair" mean anything: a badge invented today has no fact to derive from, so `grantFlair` records the award (and ensures a `profiles` row, or the grant would be stored and never rendered). Catalogue reads fall back to `BUILTIN_FLAIRS` on an empty table *and* on error, so pushing the table before seeding it doesn't strip every badge on the site; grants are read inside `getProfilesObject` but caught **separately** from the profiles read, or one un-pushed table would empty the whole map. When None cleared it too, membership looked optional and "no account" and "account, badge off" rendered identically next to a name. `resolveEarnedFlairs` returns `memberFlair()` alone for None, found by *rule* rather than by id so nothing hardcodes `brawlchemist-user`, and the picker's None tile says what it keeps

That client is the only place that knows it was the *first* one: by the time the write lands, "did they have none before" is gone, which is why `toggleFavorite` returns `firstEver` and the customizer reads `wasCustomized` off its initial props. A render-time seen-set would need a diff, a write on someone's own profile view, and it would still be telling them about something they did ten minutes ago. Every toast links somewhere — achievements to the profile (the shelf lives there; there is no achievements page), a flair to `?tab=customize`, because a new flair is a choice that just opened
- **"Possible smurf" is an observation about a record, never a claim about a person** — and the wording and the word *possible* are doing that job. `lib/profile/smurf.ts` owns the rule (rating ≥ 2300 **and** level ≤ 75 **and** ≤ 200 lifetime hours) and every number in it, because the SQL and the backfill script both quote them. **The tooltip quotes the player, not the rule**: "Possible Smurf: Account Level 21, 8h Game Time" — the two facts that earned the tag, for this account, so a reader can check the claim against the record it is about instead of against a threshold. Red (`negative`), not amber: see Design system. All three facts must be **known**: a null level means nobody has read that player's /stats yet, and "we haven't looked" is not "they're clean", so unknown returns false rather than defaulting to zero. There is no fact in the API that proves a second account (no creation date, no linked identity), so this is deliberately never phrased as a verdict. **A verified pro is never tagged**, and that exception lives in `getSmurfIds` rather than in `isPossibleSmurf`, because it is not a fact about the record — it is a fact about the profile, curated by hand. A known competitor on a new account satisfies every number in the rule (measured: one today, 2,639 elo at level 72 / 149h), and the badge that says we know who this is outranks the one that says we cannot account for them. Subtracting from the shared set is also the only edit that reaches all **fourteen** surfaces at once; doing it at the `smurfs.has(id)` call sites is the shape where the twelfth one forgotten quietly tags a pro. Free, because every one of those surfaces already reads `getProfilesMap` to render the handle the tag would sit beside. The profile page is the sole caller that computes the answer without the set, so it runs the same check itself.

The projection is three inline ints per matching row (249 rows today), so it costs what the id set did: served by `players_rating_idx`, no detoast, cached 300s.   - **The real score is on the INNER match, and we walked past it for months.** This entry used to say a scoreline was unrecoverable and that "Challengermode models a whole set as one `Match`". Its menu stays mounted and merely `hidden` (same call `RegionFilter` makes, cardinal constraint #3) because those seventy boards are real pages the old mount-on-open picker kept out of the HTML entirely. **Search is the only elastic control and OTHER has a fixed width**, so picking a legend does not reflow the row and push the cutoff onto a second line; the closed button drops "Mains" and "Ranked" because the menu is where a name has to disambiguate. Measured at 1440 with the sidebar: one 34px line even with the longest legend selected.
- **The Valhallan cutoff chip quotes one region — yours.** It answers "what rating do I need", which is about the ladder you play, not the one you happen to be reading: it follows the board when the board names a region and falls back to viewer-then-cookie on ALL, the same precedence `resolvePreferredRegion` uses. It printed three chips on ALL, which spent three cutoff walks against the 180/15min budget to answer a question nobody asks in triplicate.

They were two pages asking one question — same Valhallan pool, same region filter, and a weapon's pick rate *is* the sum of its legends'. One region control is the substance of the merge, not the layout: two pages meant two filters that could disagree, and a comparison across a region boundary is not one. Internals kept the old name on purpose — `lib/sync/live.ts`, the `live_ranked` table, the `bc-live-view` cookie — because the domain concept is still the live queue and renaming a table (or a cookie everyone already holds) to match a URL is churn with a migration attached

## External APIs

### Brawlhalla dev API (lib/brawlhalla-api.ts) — key: BRAWLHALLA_API_KEY
- Regions: `["ALL","BRZ","US-E","US-W","EU","SEA","AUS","JPN","SA","ME"]`; main three ladders US-E/EU/BRZ. **Japan disagrees with itself**: the leaderboard 400s on `region=JPS` but returns `region: "JPS"` in its rows. Canonical is `JPN` (the parameter form); `normalizeApiRegion` folds the reported spelling
- Modes: 1v1, 2v2, solo_2v2, 3v3 (3v3 is SOLO queue — single-player rows; ladder tops out Diamond, no Valhallans)
- **API never returns "Valhallan"** on `/ranked` — Diamond starts at 2000. The *leaderboard* does label it, and that label is the only source of truth: `getValhallanIds` (membership) + `getValhallanCutoff` → `isValhallan(rating, cutoff, wins)` (lib/tier.ts) as the fallback for players the id set doesn't cover. `TIER_FLOOR` has the static tier bands.
- **Valhallan is NOT a contiguous prefix of the ladder, and NOT a rating threshold.** Measured on US-E 1v1: rank 121 @ 2,507 is not Valhallan, rank 299 @ 2,138 is; the tier is interleaved all the way down and neither `rating` nor `best_rating` predicts it (it's the game's own top-N roster, and players keep the label after falling out). Consequences: (a) a walk that stops at the first non-Valhallan **page** misses 25-40% of the population — that bug shipped, and left real Valhallans rendering as Diamond on /live, the pro board and their own profile; (b) never set the cutoff to the true minimum rating — as `isValhallan`'s threshold it would promote every 2,138+ Diamond in the region. `cutoff.rating` is deliberately **the end of the unbroken run** (US-E ~2,508), which is both the honest "what do I need" answer and conservative as a fallback.
- Two walkers over `/v1/leaderboard/ranked`, different jobs, don't merge them: `discoverValhallanIds` (lib/sync/valhallan.ts) walks until a page holds **zero** Valhallans — complete but 6-8 pages/ladder, so it runs once a day in the sync-valhallan cron and persists to `valhallan_members`. `computeValhallanCutoff` (lib/sync/valhallan-cutoff.ts) walks only the unbroken prefix (1-3 pages) because it sits behind page renders. `getValhallanIds` unions both: daily-complete ∪ hourly-fresh, so either going cold shrinks the set rather than corrupting it.
- `max_results` caps at **50** (400s above it), so page depth is the only lever. `apiFetch` has no retry — a 429 mid-walk just ends it, which is why `discoverValhallanIds` returns a `complete` flag and the member write skips any ladder that came back short rather than overwriting a good row.
- **`/player/{id}/stats` reports wins per LEGEND, never per weapon**, and every legend wields two — so any per-weapon record is an attribution, not a reading. `lib/profile/lifetime-stats.ts` splits a legend's games/wins between its two weapons by time held (`timeheldweaponone`/`two`), which makes time held and share exact and the record an estimate; `/player/[id]/stats` says so above the table rather than in a footnote. Summing a legend's record into both weapons instead would double-count every match they ever played.
- **Lifetime totals are an order of magnitude above ranked ones** — "all modes" counts customs and unranked. Measured on five real accounts: 14.5k / 34.6k / 66k / 87.6k / 112k lifetime wins against season totals in the low thousands. Any threshold over lifetime numbers has to be sampled, not guessed; a first pass at 250-20,000 for the Total Wins gem put all five at the top level.
- **There is no account creation date anywhere in the API.** `/player/{id}/stats` is `level`, `xp`, `games`, `wins`, `clan`, `legends[]` and nothing else; the only date-shaped field in the whole surface is `clan_create_date`, which belongs to the clan. So "Brawlhalla account age" is not answerable — don't infer it from the ordinal of a `brawlhalla_id`, which would print a guess as a fact. Age-style achievements use `app_users.created_at` (Brawlchemist membership), and playtime proxies use `level` / lifetime `games`, which are real
- Tier strings carry division suffixes ("Gold 3") — strip via `toTier`

### Brawlhalla CMS (lib/brawlhalla-news.ts) — keyless WordPress at cms.brawlhalla.com
- **A fetch with `next: { revalidate }` has no timeout Next will honour.** When the fetch cache holds a stale entry, the patched fetch revalidates in the foreground and **strips the abort signal on purpose** (patch-fetch.js: "don't pass through signal when revalidating"), then parks the call in `pendingRevalidates`, which static generation awaits before finishing the page. A CMS that accepted the connection and went silent (measured: connects in 0.14s, never answers) held `/patch-notes` for the 60s budget three times over and failed the deploy — with a 15s signal attached the whole time, and a `Promise.race` against a timer did not help either, because the build waits on the promise the page cannot see. The shape that holds: `cache: "no-store"` on the raw fetch (the signal then reaches undici and fires — measured 5001ms for a 5s signal) inside `unstable_cache` for the hour, with `failOpen` outside it so the failure is never what gets cached. Any other third-party fetch that might hang wants the same shape, not `next: { revalidate }`.

## Admin panel

- **Users leads, and it is a table.** It lists every account — the superset, since People is keyed by brawlhalla_id and an account that never claimed a player has no row there. The table is the *scan* (linked player, pro, flair, role, plan, joined) and carries no controls; `?edituser=` opens one card above it with the three forms, the same idiom People uses for `?edit=`. That split is what keeps a row one line high; the previous stack of cards was a paragraph per account with three forms in each. The flair column runs the site's own `resolveEarnedFlairs` against the cached profiles map rather than re-deriving entitlement, or the panel would drift from what the site actually renders.
- **The panel's cost is round trips, not queries.** Every statement here answers in 1–50ms; what an operator waits on is the trip to us-west-1 and back. So both list readers are ONE query each — `listAdminUsers` and `listAdminPeople` join `players` for the username/rating rather than making a second, sequential read for them. The old comment warning that joining `players` would drag the planner over `ranked_json` was wrong: **TOAST is only read when the column is**, and constraint #2 is about `SELECT *` and jsonb *expressions*, not about joining a table that owns a blob. Measured: `Index Scan using players_pkey`, 1.08ms for the whole Users statement. The one deliberate exception is the People region, which does read `ranked_json ->> 'region'` (49.7ms / 1,285 buffers for 171 rows) because the bare `ladder_region` column resolved for 0 of them.
- Container is `max-w-[1280px]`, matching every data page on the site. It was 960 while the panel was stacked cards, and that width clipped the Users table's last column.
- **The lists are server-paginated and server-searched, and the URL is the state.** `?q=`, `?filter=`, `?page=` (lib/admin-list.ts parses them; `adminHref` in list-chrome.tsx carries them through every link). One statement per page with `count(*) over()` for the total, so a filtered count and the rows it describes come from the same read. Search is `ILIKE` over email/handle/username plus an exact id — and the account id only when the text *is* a uuid, because Postgres rejects `"enrico"` as one rather than not matching it (the smoke test caught this). The search box (`admin-search.tsx`) debounces into `router.replace` and shows its transition's pending state; it resets `page` because page 4 of a different result set is not a place. The overview strip above the tabs is one cached statement (`getAdminOverview`, tag `ADMIN_OVERVIEW_TAG`, busted by link/unlink/delete/curate) and each number links to the list that explains it. Tab links are `prefetch={false}`: every tab is a dynamic render with its own reads.
- **`after()` on a form submit is how a Save became a 300-second timeout.** `saveProfileAction` deferred a forced Brawlhalla sync into `after()`, on the reasoning that deferred work is free. It is not: the invocation stays alive until the deferred work finishes, **holding this instance's database connections** while it calls an external API and writes to the 200MB `players` table. Under pooler contention that write blocks, Vercel kills the function at 300s mid-query, and the backend is left in `ClientRead` with a transaction open — a lock on `players` and a parked Supavisor slot, which makes the next save slower still. The production logs show the whole loop: `POST /admin 303` (the redirect had already been sent) followed by "Task timed out after 300 seconds", and the reaper collecting sessions aged **288s, 295s, 303s, 341s, 359s, 378s** — every one of them a killed function. The fix is not a bigger timeout: the pull now runs **only for a pro who has no cached standing** (`hasCachedStanding`), so editing an existing pro's tier costs exactly one write and spends no API budget. The rule: never defer unbounded work that touches the database from a request path that a human is waiting on.
- **Row and card mutations return a verdict; they do not redirect.** Every admin write used to be a bare `<form action>` ending in `redirect()`, which is three problems in one shape: no feedback between the click and the new document, a full re-render that always missed the profiles cache the action had just busted (~7 round trips to say "saved"), and nothing disabled, so a second click sent the write again. `ActionForm` (app/admin/(panel)/action-form.tsx) + the `*FormAction`s in actions.ts fix all three: `useActionState` returns `{ok, message}` (lib/admin-action-result.ts), `useFormStatus` disables the button and spins for exactly as long as the action runs, and the action ends in `revalidatePath("/admin")`, which makes its **own response** carry the re-rendered page — do not add `router.refresh()` on top, that is a second full render. Destructive controls (Unlink, Delete) take `confirm`: armed on the first click, sent on the second, disarmed after 6s. The flows that still navigate (People editor, flairs, combos) keep the `?saved=` notice idiom. `saveProfileAction` defers its ranked pull into `after()` — it is an upstream call against the 180/15min budget and was sitting between the click and "saved". `apiFetch` now carries a 10s `AbortSignal.timeout`; it had none, so one silent upstream could hold a render for the whole function budget.

## Known production problems

- **ROOT CAUSE of the abandoned sessions: a connection pool that outlives the instance holding it.** Serverless instances are **frozen** between requests, not torn down, so a module-level postgres-js pool keeps its sockets open across invocations — sockets whose far end Supavisor has long since closed. On thaw the driver reuses one and writes into a dead socket. Evidence, 24h of production: **106 `write CONNECTION_CLOSED`** and **14 `CONNECT_TIMEOUT`**, against 2 function timeouts — by volume this is the top error on the project, and every other cluster is downstream of it. When that write tears mid-sequence the server is left holding an open implicit transaction in `ClientRead`, which is the abandoned session; enough of those and the pooler has nothing to hand out.
  - **It is not a slow query.** Sampled for 150s, seven distinct abandoned backends appeared across four unrelated routes, four of them the profile page's read-through freshness check — which `EXPLAIN` puts at **0.081ms, two index scans, 7 buffers**. It is simply the first query on the busiest route, so it is the one most often in flight when an instance dies. Do not go looking for a query to optimise.
  - **Two fixes, at the connection layer** (lib/db/index.ts). `max_lifetime: 60` — postgres-js defaults to a random **30–60 minutes**, a lifetime for an instance that thaws, serves one request and freezes again. Timers are suspended while frozen, but an overdue `setTimeout` runs in the timers phase on thaw, ahead of the poll phase that delivers the request, so the stale socket is usually retired before anything reaches for it. And a **retry-once** wrapper around the one entry point drizzle uses (`client.unsafe`), for the times it is not.
  - **The retry is safe because of *which* errors it retries.** `CONNECTION_CLOSED`, `CONNECTION_ENDED` and `CONNECT_TIMEOUT` are all raised before or during the socket write, so the server never saw the statement — nothing can double-apply, which is what makes it sound for writes too. Anything the server actually executed fails with a `PostgresError` carrying a SQL state, is not in that set, and is rethrown untouched. One retry, not a loop: the second attempt gets a freshly opened connection, so a second failure is not staleness and retrying again would only load a database already in trouble.
- **Two abandoned sessions are enough to take the whole site down, and that is measured.** On 2026-09-20, with exactly two backends in `state=active` / `wait_event=ClientRead` holding transactions 267s and 257s old, `select 1` through the transaction pooler failed with `57014 canceling statement due to statement timeout`. Terminating those two restored it to 1.7s immediately. The mechanism: a transaction-mode pooler pins a server connection for the life of a transaction, so an abandoned one is a connection nobody can reuse — everything queues, renders run to Vercel's 300s limit, and each killed function leaves another abandoned session. That is the feedback loop behind this project's top runtime error, and it is why an admin save "freezes the site" while the write itself is **one indexed UPDATE of five columns on a 171-row table, measured at 201ms of which ~190ms is round-trip latency**. The save was never the problem.
  - The window that matters is **threshold + cron interval**, because that is how long one abandoned session can pin a connection. It was 2min + 5min (up to seven minutes of jam); it is now **1min + 1min**. One minute is safe rather than aggressive: `statement_timeout` is 30s so nothing legitimate can be in flight longer, and the filter requires `ClientRead`, which means the backend is not executing at all.
  - `lib/sync/sessions.ts` is the one implementation. The cron runs it; **/admin → System shows the live count and offers the same button**, because the operator notices a freeze first and an invisible failure is the worst kind.
- **Abandoned database sessions, and what actually reaps them.** Serverless instances die mid-query and leave a backend holding a transaction and a Supavisor slot. Three were measured at 760s, 1,275s and 1,395s old on 2026-09-18, running `getPlayersByIds`- and profile-shaped queries. **The app holds no explicit transactions anywhere** (`grep -rn ".transaction("` is empty — every query is autocommit), so an open transaction with the client gone is *never* legitimate, which is what makes reaping them safe at any threshold. `ALTER ROLE postgres SET idle_in_transaction_session_timeout = '60s'` is applied and **it does NOT fix this** — measured, not suspected. A backend started at 15:02, after the change and therefore carrying the 60s setting, was found holding a transaction for 967s. The timeout never arms, because these sessions report `state = 'active'`, not `idle in transaction`: it is the extended-query signature of a client that sent Execute and never sent Sync, and Postgres only arms that timeout after a Sync. The setting is harmless and still covers true idle-in-transaction sessions, so it stays. **The remaining lever is a reaper we run ourselves** — `pg_terminate_backend` on any backend whose `xact_start` is older than a minute or two and whose `wait_event = 'ClientRead'`, which is safe precisely because the app holds no explicit transactions. Done by hand four times on 2026-09-18; it wants to be a cron. Query to check: `select pid, state, wait_event, now() - xact_start from pg_stat_activity where xact_start < now() - interval '90 seconds'`.
- **The top runtime error is `Vercel Runtime Timeout Error: Task timed out after 300 seconds`** — 803 occurrences / 322 users over seven days, on every route including `/`, `/player/[id]`, `/leaderboards/[mode]` and `/api/search/players`, going back to 2026-06-18. Nearly every other error cluster ("Failed query: …", caught and failed-open) is downstream of it. The pool config is already tight (`max: 4`, `idle_timeout: 20`, `fetch_types: false`), so the suspect is connection starvation rather than one slow query: serverless instances leave transactions open on `players` — `state = active`, `wait_event = ClientRead`, `xact_start` 30+ minutes old — holding both a lock and a Supavisor slot, and two of those were found and terminated by hand on 2026-09-18. `statement_timeout` cannot be set through :6543 (see lib/db/index.ts), so the lever would be `ALTER ROLE … SET statement_timeout` / `idle_in_transaction_session_timeout` on the database itself. **Not yet diagnosed or fixed** — do not assume a page that hangs is the feature you are working on.

- **There are error pages now, and there were none.** A failed render used to show Next's stock "Application error: a client-side exception has occurred" — which names no product, offers no way out, and reads like the site is gone. `app/error.tsx` offers `reset()` first because the usual cause is a function killed mid-stream and that is typically transient; it prints the **digest** and never the message, since a stack trace is noise to a visitor and a leak to everyone else. `app/global-error.tsx` is the layout-failed case and therefore ships its own `<html>` with inline styles — if the layout is broken, whatever it would have loaded probably is too. `app/not-found.tsx` keeps the site chrome so a 404 reads as this site rather than a different one, and offers the three places a lost visitor wants and nothing else.

## Design system

- Dark glass: cards `rounded-2xl border border-border/60 bg-card/50-60 backdrop-blur-sm`, rows `bg-card/40`
- Type: `font-display` headings; data is `font-mono tabular-nums`; micro-labels `font-mono text-[10px] uppercase tracking-wider text-muted-foreground`
- Tier colors: `text-tier-*` tokens + `TIER_TEXT_COLOR` map (components/site/primitives.tsx); positive/negative tokens for deltas, `warning` (amber) for caution (the error page, the admin esports-links grader). The "possible smurf" tag is `negative` red, deliberately: it was amber on the argument that red already means a loss, and amber on a dark glass row read as a highlight rather than a flag. Every token is declared **twice**, in the light `:root` and again in `.dark`; the dark value is the one that ships. A token added to only one of them still resolves by inheritance, which is how it passes a glance and ships the wrong shade
- **`toTier` lives in `lib/tier.ts`, and there is one of it.** There were three private copies (leaderboard columns, podium, home Top Pros) and they had already drifted: the home card compared the whole tier string instead of the base word, so every "Gold 3" on it resolved to null and drew no helm at all. **`RankHelm` and `RankIcon` both take `tier: Tier | null` plus `rating` and own the fallback themselves** — never guard a call site with `{tier && ...}`, because that is exactly what renders nothing for the one label the ladder uses that isn't one of the seven. "Fallen Valhallan" (held the tier, off the roster) is that label: `RankIcon` draws the game's own Fallen emblem, `RankHelm` draws the **Diamond** helm, since no Fallen helm art exists and promoting them to Valhallan would claim a membership the ladder has taken back. Below the Diamond floor both derive from the rating, which is exact. **`LegendChip` has the same contract**: `legendId` is nullable and an unresolved one draws `/assets/legends/unknown.png`, so never guard a call site with `{slug && <LegendChip …>}` or an em dash. A missing main is not missing art — it is a player whose payload we have not read a legend out of yet — and a dash in a column of portraits reads as a broken cell. The *lists* (Best Picks, the podium's top legends) still render nothing when empty, because a short list is normal there and one unknown chip would claim they play one unknown legend
- `RankHelm` has art for **all seven tiers** — it used to be Valhallan + Diamond only, and several surfaces were written around that gap ("no helm below Diamond"). Derive the tier with `tierFromRating(rating, valhallan)`, never from rating alone: Valhallan is ladder membership. Helm art is 192px / ~10KB to match — `RankHelm` renders `unoptimized` like the rest of the codebase, so the raw file is what ships and a 1000px source would be 180KB per icon
- A player's identity renders the same everywhere: verified handle + `VerifiedMark` (coloured by kind) + `FlairMark`, never the raw Brawlhalla id. `FlairMark` takes the raw selection plus the `FlairContext` entitlement is derived from (accolades, developer role, manual grants — all assembled by `flairContextFrom` off the cached profiles map), not a resolved flair, so every surface runs one entitlement rule. It is a **client** component: the catalogue lives in Postgres and reaches the browser through `FlairCatalogueProvider`, mounted once in the root layout, because flair renders on both sides of the boundary — and that boundary was already paid for by `InfoTip`. Surfaces: profile, leaderboard rows/podium, home Live Rankings, /live, OTPs, power rankings, legends, both search dropdowns, /search, /favorites
- **The podium's art slot always fills.** A curated `profiles.favorite_skin` wins; failing that `placeholderSkinFor` (lib/skins.ts) picks one from the player's main legend, which costs nothing because `top_legend_id` is already denormalised onto the row. Three rules and each matters: **never Classic** (everyone owns it, so it says nothing about the player, and it is already the art in the LegendChip beside it); **posed `art` before `icon`** (63 of 69 legends have one — the four with only icons still fall back rather than render nothing, since at 12% opacity a cropped portrait is texture either way); and **deterministic**, seeded on the brawlhalla id, because a random pick would change the card on every revalidate. It is decoration and not a claim — aria-hidden, no tooltip — so it never says "this is the skin they play". Null for the two Classic-only legends and any legend the catalogue has not caught up with (Aurus today), which leaves the slot empty exactly as before
- Filter tabs: Links (server-rendered searchParams state) in `rounded-md border bg-muted/40 p-1`, active `bg-card text-foreground shadow-[0_0_0_1px_oklch(1_0_0_/_0.06)]` — see /tournaments, /power-rankings
- Provenance chips ("Via Brawltools", "Updated <date>") ride the right end of filter rows, not heroes
- Hover affordances: slide-in glass panel (`-translate-x-full` → `group-hover/row:translate-x-0`, gradient + backdrop-blur, `motion-reduce:transition-none`) on home cards; pink Valhallan glow (`hover:border-tier-valhallan/60`) on podium/live cards; art bleeding from card right edge uses absolute Image + `maskImage: linear-gradient(to left, ...)`
- Shared components: `DataTable`/`ColDef`, `PlayerLink` (falls back to plain text on null id, prefetch={false}), `LegendChip`, `RankIcon`, `RegionPill`, `Delta`, `PageHero` (inner pages; homepage is its own launcher layout)
- Page-enter animation lives in `app/template.tsx` (remounts per route, not per query change) — tab/filter links use `scroll={false}` where viewport should hold
- Pros: verified handle + BadgeCheck replaces in-game name (table rows hover-swap to IGN; podium/home/live do NOT swap); blue "Pro Player" tag
