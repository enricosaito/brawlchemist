# Brawlchemist

Brawlhalla stats platform (dpm.lol / op.gg style). Next.js 16 App Router, React 19, Tailwind v4, Drizzle + postgres-js on Supabase (free tier), deployed on Vercel.

## Commands

- Dev: `npx next dev --turbopack -p 3137` (background) — poll with Invoke-WebRequest until 200
- Typecheck: `npx tsc --noEmit` (run before every commit)
- **`drizzle-kit push` DOES NOT PROMPT** (`--strict` is opt-in) and reconciles the DB *down to* `lib/db/schema.ts` — it DROPS any index it can't see there. It silently removed all four perf indexes once, taking username search from ~400ms back to 95s. Every index must be declared in the schema file, never only in SQL. There is no read-only "check" mode; `drizzle-kit pull` is the only safe way to inspect.
- Schema: `npm run db:push` (drizzle-kit push straight to prod Supabase — NO migration files; run deliberately), `npm run db:studio`
- Index/DDL + one-off maintenance: `db/perf-indexes.sql` and `db/reclaim-space.sql`, pasted into the Supabase SQL editor. Not runnable through DATABASE_URL — Supavisor caps statements at 2min and silently corrupts `CREATE INDEX CONCURRENTLY` (returns success, leaves `indisvalid = false`)
- **An `ALTER TABLE players` will not get its lock on the first try**, and the error it fails with ("canceling statement due to statement timeout") describes the timeout, not the cause. Serverless instances leave transactions open on `players` — `state = active`, `wait_event = ClientRead`, `xact_start` 30+ minutes ago — holding AccessShareLock forever because the client that started them is long gone. ADD COLUMN needs ACCESS EXCLUSIVE and queues behind them, and while it queues it blocks every reader too. The recipe: connect to the **session** pooler (:5432, the only one where `SET` sticks), `SET lock_timeout = '3s'` so a failed attempt fails fast instead of stalling the site, `pg_terminate_backend` the ClientRead zombies older than 5 minutes, then retry. Adding a nullable column with no default is metadata-only, so it does not rewrite the 200MB table once the lock is granted
- PowerShell 5.1 quirk: commit messages / PR bodies containing `"` get mangled as inline args — ALWAYS `git commit -F <file>` and `gh pr create --body-file <file>`
- `gh pr create` sometimes claims the branch isn't pushed — retry with explicit `--head <branch>`

## Cardinal constraints (override convenience every time)

1. **Brawlhalla API: 180 req/15min, fully budgeted.** New features must NOT add API calls. Piggyback existing fetch paths; read from our own DB/caches. `upsertPlayerRanked()` (lib/sync/players.ts) is the single chokepoint where every fresh `/ranked` payload lands (profile views + crons) — snapshot-style features hook there.
2. **Supabase free tier: egress matters — 5GB/mo, and it has been blown 3x.** Never `SELECT *` on tables with jsonb. Select narrow columns; `getPlayersByIds(ids, { includeRankedJson: false })` for anything that doesn't read legends. The two offenders found by `pg_stat_statements` (order by `rows` desc — it's the best egress proxy available): sync-live reading the whole `live_ranked` snapshot every 5min (180M rows ≈ 16GB) and the profile page pulling `ranked_json` (~6.3KB/row) just to test freshness across 1.2M views (≈7.6GB). **A cron that diffs a snapshot must read only the ids it is about to reconcile, and only the columns it compares.**
3. **Crawlers never spend Brawlhalla API budget.** 53% of profile views are bots (Bingbot alone 42%), and each used to trigger /ranked + /stats + /guild — three calls against the 180/15min budget — leaving real visitors on the 429 fallback. `isCrawler()` (lib/bots.ts) routes them to stored data at any age; `loadRanked` returns `source: "db-crawler"` and the page skips every upstream call. Separate from middleware's `BLOCKED_BOTS` (hard 403 for AI/SEO scrapers) — these are crawlers we WANT indexing us.
4. **Supabase free tier: 500MB database size.** Storage is as scarce as egress and the project has been over. Anything written per page view needs a retention window AND a small row — `fetch_log` hit 362MB (59% of quota) because it stored a ~125-byte User-Agent on every one of ~15k rows/day forever; it now stores a ~10-byte `clientLabel()` with a 14-day prune. Remember DELETE does not shrink the file on disk — only `VACUUM FULL` moves Supabase's size metric (see `db/reclaim-space.sql`). Next lever if it grows again is `players` (200MB, all `ranked_json`): evict the blob for cold, non-Valhallan players rather than touching the aggregation pool.
5. **Everything fails open — OUTSIDE the cache, never inside.** Enrichment lookups (profiles map, players cache, CM, esports) degrade to plain rendering rather than taking down a page. But a `catch` *inside* `unstable_cache` turns that virtue into an outage: the empty value is a successful return, so the cache stores it and serves it as fact for the whole revalidate window, and every failed refresh renews it. On 2026-09-18 one `CONNECT_TIMEOUT` to the pooler emptied `getProfilesObject` (1h window) and for an hour **no pro had a handle anywhere on the site** — no linked-account badge, no flair, no favourite skin, no esports title — while all four of its reads answered in under two seconds when measured. So: **a cached function must throw**; a thrown error is not cached, and the first success repairs everything. `failOpen` (lib/sync/fail-open.ts) is the wrapper, and it carries a 10s per-reader cooldown so "don't cache the failure" doesn't become "retry on every request" against a database that is actually down. Applies to `getProfilesObject`, `getFlairObject`, `getCustomization`, `getFlairCatalogueCached`, `getFlairGrantsObject`, `getSmurfIdList`, `getFavoriteIds` — all six had it.
6. **Never put a `players` full-table scan on a render path.** `players` is ~90k rows / ~200MB, almost all of it `ranked_json` in TOAST. Any query that evaluates a `ranked_json` expression in a WHERE/ORDER BY across the table detoasts all of it. Order search/list queries by the denormalised `rating` column (see #8), not by a jsonb expression.

   **The Valhallan aggregations broke this rule for months, in the one place this file called legitimate.** Every one of them filtered `(ranked_json->>'rating')::int >= 2300` — re-deriving from the blob the value `players.rating` is denormalised to hold — so the filter meant to narrow 90k rows to 2k read all 90k first. That is why they "legitimately take 25–95s": they never had to. Swapping to the indexed column, with output proved identical (2,043 rows both ways, zero disagreement in either direction):

   | | via `ranked_json` | via `rating` | |
   |---|---|---|---|
   | sample count | 9,613ms | 571ms | 17× |
   | legend stats, global | 16,223ms | 2,017ms | 8× |
   | legend stats, US-E | 16,766ms | 531ms | **31×** |
   | mainer counts | 31,072ms | 570ms | **54×** |
   | top mainers | 13,535ms | 704ms | 19× |

   `valhallanRatingClause()` is now the single place that asks the question, so the next aggregation cannot quietly reintroduce the slow form. `regionClause` still reads `ranked_json->>'region'` and costs nothing, because the index narrows first and only those 2,043 rows are detoasted — which is why the *regional* case is the fastest of the three. They stay behind `unstable_cache` (`VALHALLAN_STATS_TAG`, 6h): call the exported `get*`, never `compute*`. **A cache miss still computes on a user's request**, and the key includes `{region, method, minGames}`, so it is ~22 entries that miss independently rather than one that warms once — which is the remaining reason to move this into the cron and have readers only SELECT.

   `lib/sync/admin-stats.ts` still does a real full scan (16s): its CASE needs `ranked_json->>'tier'`, which exists nowhere else, so the detoast is unavoidable without a column. Admin-only and it fails open. `lib/sync/otps.ts` looks similar and is not — it filters on the indexed `top_legend_id` (1.5s) and only projects rating.

   **A rank nobody can reproduce is not a rank.** `computeTopValhallanMainers` ordered its windows by rating alone, so players on the same rating got an arbitrary order — swapping the filter appeared to change 70 of 209 rows when the row set was provably identical, and two players swapped in and out of a `rn <= 3` cut. Both windows now break ties on `brawlhalla_id`, which made the before/after exactly identical and the query repeatable.
7. **The Brawlhalla API double-encodes UTF-8.** It serves `application/json` but builds its JSON escapes from already-UTF-8 bytes treated as Latin-1, so "Areté" arrives as "AretÃ©". Not a font bug — no display change fixes it. `repairJson()` (lib/text.ts) is deliberately conservative (telltale byte pattern + exact round-trip check) because an eager version corrupts legitimately non-ASCII names; 3,313 stored usernames needed repair and 16 fail the round-trip check (names the API truncated mid-codepoint) and are left alone. **It must be applied on BOTH edges, not just the API one.** `apiFetch` cleans payloads arriving fresh from upstream, but `players.ranked_json` still holds blobs written before that landed, and the profile page serves the stored blob whenever the row is fresh (6h idle window), the visitor is a crawler, or upstream 429s — i.e. the mangled name survived on exactly the paths that skip the API. So `getPlayerRankedJson` and `getPlayersByIds` repair on the way out too. `live_ranked.players` needs no backfill: the cron rewrites it every 5 min through `apiFetch`. Repairing the username column alone is NOT enough — the profile page renders `ranked_json.name`, not `players.username`.
8. **Ordering must use an indexed scalar, bare.** `players.rating` is denormalised out of `ranked_json` by `upsertPlayerRanked` for exactly this. Do NOT order by a `ranked_json` expression (detoasts ~200MB, measured 95s) and do NOT wrap the column in `coalesce()` — that alone made `players_rating_idx` unusable and a two-character search went 0.4s → 15s. `ladder_rating` and `ladder_region` are both dead columns: only the search-index harvest writes them and nothing calls that harvest (measured: 0 non-null `ladder_region` out of 95,635 rows, while 94,928 have one in `ranked_json`). Anything needing a region must coalesce — `getPlayersByIds(ids, { withRegion: true })` does, opt-in because it detoasts per row. The bare column silently rendered no region pill on /favorites for as long as that page has existed.

   **An index only serves an ORDER BY whose null ordering matches it.** `players_top_legend_rating_idx` is `(top_legend_id, rating DESC NULLS LAST)`; querying it with a bare `ORDER BY rating DESC` (which means NULLS FIRST) drops the planner onto a bitmap heap scan — measured 1.9s vs 0.05ms for the same three rows. Same family of trap as wrapping the column in `coalesce()`.
9. **Supavisor pool is small and shared.** postgres-js defaults to `max: 10` with no idle timeout, so each serverless instance parks ten pooler slots forever; `lib/db/index.ts` caps it. The transaction pooler (:6543) silently IGNORES a `statement_timeout` startup param and ignores `SET` — for DDL or anything needing a longer/shorter timeout, connect to the session pooler (:5432) where `SET statement_timeout` sticks.

   **But `ALTER ROLE` DOES reach backends through both poolers.** A role default lives in `pg_db_role_setting` and is applied when a *backend* starts, which is upstream of anything Supavisor drops — so it is the one way to set a real per-session default for the app. Measured: after `ALTER ROLE postgres SET idle_in_transaction_session_timeout = '60s'`, a newly-created backend reached through :6543 reports `1min` while pre-existing pooled backends still report `0` until Supavisor recycles them. We connect as `postgres`, which (unlike `authenticated`/`anon`, capped at 8s/3s) had **no** overrides at all — it inherited `statement_timeout = 2min` and `idle_in_transaction_session_timeout = 0`. Do not tighten `statement_timeout` below ~2min: the sanctioned Valhallan aggregations legitimately take 25–95s (measured 26.7s for a full `ranked_json` scan today).

## Data architecture

- `players` — PK brawlhalla_id; `ranked_json` (full GetPlayerRanked, drift-safe jsonb), `top_legend_id` (pre-computed main), ladder snapshot scalars, guild fields, `last_synced`
- `profiles` — admin-curated verified pros (handle, favorite skin); `getProfilesMap()` cached 300s, tag "profiles"
- `user_customizations` — what an owner chooses about their own profile: banner, flair, favourite legends, links. **Every field is a choice from a list we control.** There was a freeform bio; it was the only thing on the site whose contents nobody could check, and it is gone — including the `ProfileCustomization` card, which held nothing else. All customization now renders in the profile card (header), never in a section below it
- **A profile link must point at the site its glyph names.** `SOCIAL_HOSTS` (lib/profile/social.ts) is the allow-list and `isAllowedSocialUrl` the check; matching is exact-host or true subdomain, never `includes`, so `evil-x.com` and `x.com.evil.net` are both rejected while `www.` and `m.` are not. There was a sixth kind, `website`, that took any https URL — one profile was using it to link a porn site from a page with our name on it. Removing the kind alone would have fixed nothing, because nothing checked the host either: the same URL filed under "twitch" would have drawn the Twitch glyph and linked straight to it. **The check runs on the way OUT as well as in** (`parseSocialLinks`), which is what let the rule be tightened with no migration — a row written before it existed simply stops being returned, so it stops rendering the deploy it ships in rather than waiting on a cleanup. Same both-edges shape as `repairJson`. The panel runs the same check so a rejected URL is named rather than silently dropped on save
- **Only the links are gated, and the gate cannot destroy data.** A favourite legend is a pick from a fixed roster — nothing to moderate, nobody to vet — so it is open to everyone; links put an outbound URL on a public page, so they stay with verified pros and developers. `saveProfileFieldsAction` **carries the stored links through** rather than writing `[]` when the caller isn't entitled: refusing the whole save would lose their legends too, and writing empty would let a failed `getProfile` read, or a pro whose verification lapsed, silently delete links they had already saved. Not entitled means "cannot change these", never "these are now empty"
- **Every customizer change is local until Save, and every one of them previews on the card above.** The two halves go together and neither works alone: holding changes locally is what makes Cancel possible, and putting the pending value on the header is what makes a banner, a skin or a main judgeable at all — a 32px swatch tells you nothing. `ProfilePreviewProvider` carries banner, flair, skin and legends; `PreviewBannerWash`, `PreviewFlair`, `PreviewSkin` and `ProfileIdentityRow` read it and fall back to the server value, and every one returns the server value untouched when there is no provider. Two traps it is built around: the skin slot is **tri-state** (`undefined` = nothing pending, `null` = pending-none), because collapsing them makes *clearing* your skin the one change the preview cannot show; and the preview carries legends as resolved `{name, slug}`, not roster ids, because whoever holds the ids needs `LEGEND_ROSTER` to draw them and putting that in the identity row ships all seventy legends to every visitor for a preview only the owner can trigger
- **Saving the customizer does a real document load**, not `router.refresh()` + `router.push()`. Those go through the client router, which serves the profile out of its own RSC cache for an entry it already had, so a save could land and the page you arrived back on still showed the old skin. The reload is deferred by ~0.9s (2.6s when an achievement fired) because a document load tears down the toast layer — and the unlock toast is the one thing on the page that exists only for that moment, announced at the click that earned it and never re-derived
- `app_users` — one row per Supabase identity. **Two independent account axes, never one enum** (lib/auth/account.ts owns both lists and everything they grant): `account_role` = permission (`developer` | `partner` | `user`), `plan` = subscription (`free` | `supporter` | `founder`). Split because a Partner can also be a Founder, and because a lapsed card must never be able to revoke admin. "Linked User" is a **sixth level that is derived, not stored** — a `user` who owns a `profiles.userId`; storing it would drift, since that link moves in three places. Reads go through `parseRole`/`parsePlan`, so unknown values degrade to `user`/`free` (which is why the legacy `plan='premium'` needed no backfill)
- **A page-level `redirect()` is not an auth gate on a route with a `loading.tsx`.** `redirect()` only becomes a 307 while the response has not started; a streamed route sends its shell first, so the redirect degrades to a client-side navigation and the route answers **200 with a shell** to anything without JavaScript. /favorites had a loading.tsx and /account did not, which is the whole reason one of them gated and the other silently didn't. Signed-in-only routes are therefore listed in `SIGNED_IN_ONLY` in `middleware.ts`, which decides before a byte is rendered; `updateSession` hands back `signedIn` for free, since the cookie refresh already reads the claims. The in-page checks stay as defence in depth for anything not on that list.
- **A server component importing a plain value out of a `"use client"` module gets a client reference, not the value** — and it does not throw. The proxy's properties read as `undefined`, `cn()` drops them, and you get markup missing exactly the classes you thought you shared. /meta-picks shipped this for a day: the table's column widths were exported from `components/site/meta-table.tsx`, the server-rendered detail panel read `META_COL.stat` off the proxy, and every width silently vanished — measured 57px and 44px where 76 and 84 were declared, with the numbers a few pixels off their headings. Constants shared across the boundary live in a plain module (`lib/meta-columns.ts`); only components should be imported from a client file.
- **`public/assets` is foldered, and two things pin a file's path.** Art lives under `avatars/`, `badges/`, `flairs/`, `gems/`, `legends/`, `media/`, `ranks/` (helms, rank icons and banners), `regions/`, `stances/`, `weapons/`. What stays loose at the root is the set whose paths are **stored in Postgres** — `flairs.src` and `profiles.favorite_skin.src` — because moving one 404s in production until the row is updated, and the deploy and the data edit cannot land at the same instant. Moving those needs a two-step: ship a copy at the new path, update the rows, delete the old. **Before deleting anything as "unused", remember paths are also built dynamically**: `/assets/ranks/Banner_Rank_${tier}.webp` and `/assets/legends/${slug}.png` never appear as whole strings in the source, so a naive grep reports all seven rank banners and every legend portrait as orphans. An audit that does not expand those two patterns will happily delete the profile header's artwork.
- **Admin access is a role, not a password.** `isAdmin()` = signed-in account with `account_role='developer'`, OR an email in `ADMIN_BOOTSTRAP_EMAILS` (env-only, nothing in the app can write it — it's the bootstrap, since Developer can only be granted from inside the panel, and the way back in after a mis-demotion). Fails **closed**: any DB/auth error means not-admin. The trade vs. the old shared password is that /admin now depends on Supabase auth being up. Role writes live only in `setAccountRole`, which refuses a self-change — that's what makes self-elevation structural rather than merely unrendered
- **`BUILTIN_FLAIRS` is a fallback, not a seed.** It is consulted only when the `flairs` read comes back empty or throws, and that table has been seeded since the admin panel landed — so adding a badge to the array alone puts it in the code and nowhere anyone can see. A new flair needs its row too (Early Tester was added that way: `manual` rule, because there is no fact on a player record that says "was here early").
- `flairs` + `flair_grants` — the badge catalogue, curated at /admin, and the ledger for hand-awarded ones. **The catalogue is data; entitlement is code.** `flairs.rule` is a closed allow-list (`developer` | `claimed` | `achievement` + `rule_value` | `manual`) read through `parseFlairRule` — an operator picks which rule a badge uses and cannot author a new one, because "has this player earned it" is only answerable against the player record. `manual` is what makes "create a flair" mean anything: a badge invented today has no fact to derive from, so `grantFlair` records the award (and ensures a `profiles` row, or the grant would be stored and never rendered). Catalogue reads fall back to `BUILTIN_FLAIRS` on an empty table *and* on error, so pushing the table before seeding it doesn't strip every badge on the site; grants are read inside `getProfilesObject` but caught **separately** from the profiles read, or one un-pushed table would empty the whole map. A **selection** (`user_customizations.flair_id`) is still only a preference, validated for shape and never for catalogue membership — `resolveFlair` re-derives on every render, so an id naming nothing falls back rather than being dropped on write. **The membership badge is the one thing a selection cannot turn off.** `FLAIR_NONE` clears the badge you *chose to fly*; the `claimed` flair is not one of the things you were choosing between — it is derived from `profiles.userId` on every render and says the profile belongs to an account here. When None cleared it too, membership looked optional and "no account" and "account, badge off" rendered identically next to a name. `resolveEarnedFlairs` returns `memberFlair()` alone for None, found by *rule* rather than by id so nothing hardcodes `brawlchemist-user`, and the picker's None tile says what it keeps
- **Unlocks are announced at the click that earned them**, never by diffing on render. `components/site/unlock-toast.tsx` (Sonner, bottom-right, `toast.custom` so the card is ours) is called from the client that performed the action — favouriting, saving the customizer, finishing a claim. That client is the only place that knows it was the *first* one: by the time the write lands, "did they have none before" is gone, which is why `toggleFavorite` returns `firstEver` and the customizer reads `wasCustomized` off its initial props. A render-time seen-set would need a diff, a write on someone's own profile view, and it would still be telling them about something they did ten minutes ago. Every toast links somewhere — achievements to the profile (the shelf lives there; there is no achievements page), a flair to `?tab=customize`, because a new flair is a choice that just opened
- **"Possible smurf" is an observation about a record, never a claim about a person** — and the wording, the amber, and the word *possible* are all doing that job. `lib/profile/smurf.ts` owns the rule (rating ≥ 2300 **and** level ≤ 75 **and** ≤ 200 lifetime hours) and every number in it, because the SQL, the tooltip and the backfill script all quote them. All three facts must be **known**: a null level means nobody has read that player's /stats yet, and "we haven't looked" is not "they're clean", so unknown returns false rather than defaulting to zero. There is no fact in the API that proves a second account (no creation date, no linked identity), so this is deliberately never phrased as a verdict. **A verified pro is never tagged**, and that exception lives in `getSmurfIds` rather than in `isPossibleSmurf`, because it is not a fact about the record — it is a fact about the profile, curated by hand. A known competitor on a new account satisfies every number in the rule (measured: one today, 2,639 elo at level 72 / 149h), and the badge that says we know who this is outranks the one that says we cannot account for them. Subtracting from the shared set is also the only edit that reaches all **fourteen** surfaces at once; doing it at the `smurfs.has(id)` call sites is the shape where the twelfth one forgotten quietly tags a pro. Free, because every one of those surfaces already reads `getProfilesMap` to render the handle the tag would sit beside. The profile page is the sole caller that computes the answer without the set, so it runs the same check itself.
  - Level and playtime are the only two facts the rule needs that `/ranked` does not carry, so they are **denormalised onto `players` (`level`, `playtime_seconds`, `stats_synced`) from payloads the site already fetched** — `recordPlayerStats` behind `after()` on the profile page, the same piggyback `maybeInsertSnapshot` makes on `upsertPlayerRanked`. Coverage therefore follows attention. `scripts/sync-player-stats.mjs` is the cold-start backfill and is the **one thing in the repo that spends API budget on its own**: 6 req/min by default (half of the 12/min ceiling), highest rating first so stopping it early leaves the top of the ladder covered, 60s backoff on a 429.
  - List views read `getSmurfIds()` (lib/sync/smurf.ts) — one cached `Set` for the whole site, same shape and same reason as `getFlairMap`. Measured 73ms / 1,979 buffers on `players_rating_idx`, no detoast, cached 300s. The **profile** page computes the answer from the live /stats payload instead and falls back to the set only for crawler and 429 views, which is what keeps a profile agreeing with the leaderboard it was linked from.
  - Account level caps at **100**, and everyone in the top few hundred is already there — so `level ≤ 75` is the binding half of the rule and the tag is meant to be rare.
- **Esports titles live in one table, `esports_titles`, told apart by `source`.** They used to have two homes — a jsonb column an operator typed into and this table, written by `scripts/sync-esports-titles.mjs` off Challengermode placements — and `toPreview` merged them by **comparing strings**. That worked only while the wordings happened to match: a derivation phrased "World Champion 2v2 '23" against a typed "2v2 World Champion '23" would have shown the same win twice. The two are not redundant but **complementary**, which is why neither could just be deleted: the script structurally cannot reach the pre-Challengermode history (BCX '21, the SGG-era worlds), so those can only ever be typed. `source='manual'` rows carry null `year`/`mode`/`tournament_*` because those describe a *derivation*, and a hand-typed honour has none. The id is a function of its inputs either way (`${tournamentId}:${brawlhallaId}`, or `manual:${brawlhallaId}:${md5(title)}`), so writing the same title twice is idempotent. `profiles.achievements` is the dead column left behind — still declared for one deploy so the previously-running build can keep selecting it, then droppable.
- **Esports match history comes from Challengermode brackets, and nothing else can give it.** brawltools has NO match endpoint — /v2/match, /v2/player/{id}/matches and friends all 404, placements are per-player only. Challengermode has the whole bracket, but `Tournament.stages` is an **INTERFACE**: select it plainly and you get `index`/`format`/`lineupCount` and conclude the data is not there. The matches are behind inline fragments — `... on TournamentEliminationStage { brackets { rounds { matchSeriesPage` (also `TournamentGroupStage.groups` and `TournamentSwissStage.rounds`). `first: 200` pulls 966 of a 512-lineup double elimination's ~1,023 matches in ONE request, so a tournament costs two or three calls rather than twenty-five. Only CM-hosted events have brackets — 77 of 240 official ones, **all of them 2025-2026**. Measured by host per year: 2021 (60), 2022 (57), 2023 (52) and 2024 (52) are **100% SGG** and have no bracket at all; 2025 is 36 CM against 14 SGG; 2026 is wholly CM. So match history begins in **2025** and even 2025 is partial. The SGG era therefore runs through **2024**, not "≤2021" as the Challengermode note below used to say. Costs **zero** Brawlhalla API budget.
  - **Identity is the hard part, and it is proved rather than matched.** Challengermode never exposes a Brawlhalla account id: its `gameAccountId` is a CM-internal UUID and `GameAccount.displayName` is an in-game name ("BBBalloonBoy7") that does not match what we store. The only bridge is brawltools, which holds `cmPlayerId` and `brawlhallaId` on one record, so a member is identified by UUID equality (verified: megD, brawlhalla 33116656, is `6c92f7c2-…` on both sides). Measured across 122 verified pros: **84** resolve directly, **10 compete on a different account than the one their profile curates** (Ahmet among them — profile 45653969, esports 119319655), and **28** are known to brawltools as competitors with no `brawlhallaId` at all. Those 28 cannot have a match history, and that is honest rather than broken.
  - **`profiles.cm_player_id` is the curated fix, and the Brawlhalla id was the wrong key.** `esports_brawlhalla_id` came first and stored the account a pro competes on — which the bridge only ever used to *look up* a Challengermode id. brawltools holds a `cmPlayerId` for nearly every competitor and a `brawlhallaId` for very few: of the 38 pros with no match history, **only 6** had one, so keying on it made the other 32 unlinkable for no reason. It never held a value; `cm_player_id` replaces it and the old column stays declared for one deploy so the running build can keep selecting it, the same two-step `profiles.achievements` took. Rows are still written under the profile's **canonical** `brawlhalla_id`, so this never leaks past the sync script.
  - **/admin → Esports links gathers the evidence and grades it; it never writes.** The chain runs across three sources: brawltools finds a competitor from the handle, Challengermode gives the in-game name that competitor set on their **own** game account (`GameAccount.displayName`), and we hold the in-game name of the account already curated as this pro. When the last two agree the player has effectively told us which account is theirs — Ahmet is the case that proves it, profile 45653969 is "HaciTCH" in game and the competitor "Ahmet_" declares "HaciTCH". That is not a handle match. It is still **not proof**: Brawlhalla names are not unique, and two people called "MAK" close the same chain, so a human asserts and unlinking is one click — a wrong assertion has to be as cheap to take back as it was to make. Measured over the 38: 3 exact, 8 near, 23 weak, 4 with no candidate. The screen lists only pros who have no history **or** are already linked — listing all 122 meant 84 rows needing no decision and, at two network calls each, 55s to say so (18.8s filtered).
  - **The map is built from our side, not the bracket's.** One brawltools lookup per curated pro (~122 a run), and a bracket member counts only if their UUID is in it. Resolving every entrant by name search instead would be thousands of calls per tournament and would trade proof for a guess.
  - `esports_matches` stores **one row per (match, tracked player)**, the same shape `esports_titles` uses and for the same reason: every read is "this player's matches", so one indexed scan on `(brawlhalla_id, started_at DESC NULLS LAST)` answers it and nothing is joined or flipped at render time. A pro-vs-pro match therefore stores two rows, which is the point. `won` is **nullable** — a bye, a draw and a result that never went final are all "not a loss", and false would invent a defeat. Byes are skipped entirely: a series with fewer than two lineups is not a match. `scripts/sync-esports-matches.mjs` is idempotent on `${matchSeriesId}:${brawlhallaId}`; completed tournaments never change, so re-walking one is wasted work rather than wrong work.
  - **`bestOf` is a lie, and the legend statistics are what expose it.** Challengermode reports every match in these events as `bestOf: 1`, including a championship final that used four of five game slots. The real length is recoverable: each player carries per-game statistics named `Game1_Legend`..`Game5_Legend`, "NA" for a game never played, so counting the real picks gives `games_played` — taking the **higher of the two sides**, because one player reporting and the other not is the common case. All 64 legend spellings Challengermode uses map onto `LEGEND_ROSTER` once case and punctuation are dropped (verified across two tournaments, zero unmatched), so they are stored as slugs and render as `LegendChip`s. The **sequence** is kept rather than a set — "Lucien, Lucien, Lucien, Diana, Diana" is a counterpick that won a set, and a set would throw that away; the renderer collapses consecutive repeats so four games on one legend is one chip.
  - **It is deliberately NOT turned into a score.** The winner takes ceil(bestOf/2), so games-played would give "3–1" if the format were known — but finals are Bo5 and early rounds Bo3 by a per-event convention the API never states, and a three-game series is 2–1 or 3–0 depending which. There are no per-game result nodes to settle it: Challengermode models a whole set as **one** `Match` and the games exist only in these statistics. So the row prints "4G" (a fact) and never a scoreline (a guess).
  - **There is no map data anywhere.** `GameSession.lobbyInformation` is `gameSessionId` and `lobbyName`, and nothing else in the schema carries one. `durationInMilliseconds` is real, though — the 2026 NA final ran 19m35s.
  - **Coverage is by round, and it is the shape you would want.** The statistics are self-reported, so: quarter/semi/finals in both brackets are **100%**, the mid rounds are **0%**, and early rounds run 2–42% — measured on Summer Championship NA 2026. It also varies by *tournament*, not only by round: some events have deep rounds with nothing reported. The picks therefore land on exactly the matches someone opens a profile to see, and the ~two-thirds without them render as they did before the feature existed — no gap, no placeholder, same rule `LegendChip` already follows. **Cost was the surprise: none.** The statistics ride inside the existing bracket walk, so it is still one query per tournament (measured 8.3s / 0.43MB for a 966-series bracket), no N+1, and zero Brawlhalla budget.
  - **A finish is a fact about the run, and it lives on every row of it.** Challengermode carries placements on the tournament roster, completely — 77 of 77 events resolved. `placement_rank` is `bestPlacement` (1, 2, 3, 5, 7, 9, 13…), which is what the ordinal renders from; `placement_display` keeps Challengermode's own string ("5 - 6", "9 - 12"), because finishing joint-fifth is not the same claim as finishing fifth. Denormalised onto each row rather than given its own table: the alternative is one number per (tournament, player) and a join on a page that is otherwise a single indexed scan. Podium colours only — gold, silver, bronze — since painting 9th gold-adjacent would make every card shout.
  - **The runs are `<details>`, and the most recent is open.** A profile with nineteen events was nineteen expanded lists, and reaching the tenth meant scrolling past four hundred rows (measured: 6 visible against 125 hidden once folded). Native `<details>`/`<summary>` keeps the open state in the browser, so the section stays a **server component** — no hydration for a disclosure, and it works before JavaScript arrives. The card itself is the one `/tournaments` uses (stacked date block, name, chips), so an event looks the same wherever the site shows one.
  - **A Challengermode username is not an identity.** "lopesbrawlhalla" is the Lopes on our leaderboard, and printing the raw one made a bracket read as a list of strangers. A participant resolved to a Brawlhalla account renders handle + `VerifiedMark` + `FlairMark` and links to the profile, exactly as every other surface does; one that did not resolve keeps the Challengermode name as **plain text**, because a name we cannot vouch for must not look like a link to a player we can. The date moved to the run header for the same reason the score never became a scoreline: sixty rows repeating one day's date is one fact printed sixty times.
  - **`--resume` has to know what "already walked" means TODAY.** Its test was `games_played is not null`, correct when written and wrong the moment placements were added — the 22 events walked before that carried a set length and no finish, so a resume skipped precisely the rows it existed to fill and reported success. It now requires every field the current walk produces, and **each new field needs its own clause**: the failure is silent, and it has already happened once.
  - The **Esports tab** sits between Ranked and Achievements — Ranked and Esports are both records of matches played, and the two derived shelves belong together after them. It appears only for a player with rows, so `ProfileSectionNav` sizes its grid from the section count instead of a fixed `grid-cols-3`. Matches group by tournament because a career is read as *runs*; tournaments run newest first and the matches inside one run **oldest** first, because a list is a history and a bracket is a story.
- **Three accolade systems, one profile, and they are not interchangeable.** *Esports titles* (above) are facts about a career. *Achievements* (`lib/profile/achievements.ts`) are derived and binary. *Gems* (`lib/profile/gems.ts`) are derived and **graded** — one object whose level *is* the number, which is the right shape for anything with a metric behind it: minting one achievement per elo threshold would put five near-identical badges on the shelf and call four of them locked. Gems read the same `AchievementContext` and obey the same hard rule (no query on a render path). Each level carries an optional `src`, so a tinted facet SVG renders until sprites land and adding art is filling in a field, not changing a component.
- The pro accolades were called *achievements* until the profile grew an actual achievement system. The TS property is `esportsTitles`; **the column is still `achievements`**, mapped in the schema, because `drizzle-kit push` has no rename — it would drop one column and add another and take the data with it. Same reason `flairs.rule` keeps the stored token `'achievement'`: `parseFlairRule` degrades anything unrecognised to `manual`, so renaming it would silently demote the World Champion flair between the deploy and the data edit. **That rename had one trap tsc could not catch**: `flairContextFrom` takes a structural type, and an optional property the argument no longer has is still assignable — so `FlairContext.achievements` reading a renamed `preview.esportsTitles` compiled clean and would have silently dropped every accolade-based flair.
- **Achievements are not flair**, and the split is deliberate. Flair answers "which badge do you fly" — a rarity-ranked catalogue you pick one from, rendered beside your name everywhere. An achievement answers "what have you done" — the whole set renders at once, profile only, and **locked ones show as silhouettes**, because the unearned half is the point. That is why the catalogue is code (`lib/profile/achievements.ts`) rather than a curated table: a flair's rule comes from a short allow-list an operator picks from, while an achievement's rule *is* the achievement, so the entry and its predicate live together. Predicates can't cross the RSC boundary, so `AchievementShelf` evaluates them server-side and ships the answer — but the module is importable from the client on purpose, so the unlock toast names and pictures a badge from the same catalogue the shelf renders rather than duplicating the presentational fields. Adding one is art in `public/assets/badges/` plus an entry; the hard rule is that a predicate may only read `AchievementContext`, which carries what the profile header already computed. A badge that needs its own query does not get written
- `live_ranked` — top-500 per queue, diffed every 5 min; session anchors give eloDiff/rankDiff at read time; powers /live + daily movers
- `ranked_snapshots` — rating history; written by `maybeInsertSnapshot` inside `upsertPlayerRanked` (deduped on unchanged rating+games); 180d prune in sync-valhallan cron; chart on profile Overview
- Crons (vercel.ts; pause toggles in cron_controls via /admin): sync-leaderboard */5, sync-live */5, sync-valhallan daily 6AM
- **"My region" is one idea with one implementation.** `resolvePreferredRegion` (lib/region-preference.ts) is shared by /queue and /leaderboards: explicit `?region=` → the signed-in viewer's own region (`getViewerDefaultRegion`, from their linked profile) → the region they last had open (one cookie, shared by both pages) → ALL. A linked account outranks the cookie deliberately — if you've proved you play BRZ, a remembered click from a session spent browsing EU should not beat the account you own. Resolved server-side because that is the point of a cookie over localStorage: the right ladder in the first paint rather than the default plus a correction. All 43 linked accounts resolve to a region today, so the linked tier is real, not a no-op. The cookie keeps its old `bc-live-view` name and `"queue:region"` shape — renaming it would be tidier and would silently forget every region anyone has chosen.
- **The leaderboard control row is one line and asks one question: which region, which ranking.** REGION leads because it qualifies everything after it; TYPE is a tablist of the three boards people come for (deliberately roomier tabs); OTHER is a dropdown holding *everything else* — Ranked Solo 2v2, Ranked 3v3, Pros only and all seventy `<Legend> Mains` boards. There is no separate LEGEND picker: a mains board is another slice of the same ladder, and two dropdowns that could both light at once claimed a selection the page can only make one of, so TYPE also goes dark behind an active mains board. Seventy-three entries is why OTHER is a dropdown while TYPE stays tabs — that is the *only* reason the two groups render differently. Its menu stays mounted and merely `hidden` (same call `RegionFilter` makes, cardinal constraint #3) because those seventy boards are real pages the old mount-on-open picker kept out of the HTML entirely. **Search is the only elastic control and OTHER has a fixed width**, so picking a legend does not reflow the row and push the cutoff onto a second line; the closed button drops "Mains" and "Ranked" because the menu is where a name has to disambiguate. Measured at 1440 with the sidebar: one 34px line even with the longest legend selected.
- **The Valhallan cutoff chip quotes one region — yours.** It answers "what rating do I need", which is about the ladder you play, not the one you happen to be reading: it follows the board when the board names a region and falls back to viewer-then-cookie on ALL, the same precedence `resolvePreferredRegion` uses. It printed three chips on ALL, which spent three cutoff walks against the 180/15min budget to answer a question nobody asks in triplicate.
- **/meta-picks is the legend meta and the weapon meta together**; `/legends` and `/weapons` are permanent (308) redirects to it. They were two pages asking one question — same Valhallan pool, same region filter, and a weapon's pick rate *is* the sum of its legends'. One region control is the substance of the merge, not the layout: two pages meant two filters that could disagree, and a comparison across a region boundary is not one. Both tables carry the same four columns (pick, win, games) because they are meant to be read across; the legend side is capped to the fifteen rows the weapon side has and scrolls past that, so seventy names beside fifteen don't turn the page into a column with a stub next to it
- **There is one pros board**: the `pro=1` view of the ladder, reached from OTHER. `/leaderboards/pro` was a second implementation with its own region list and its own column build, linked from nowhere and already drifting; it is now a permanent (308) redirect in next.config.mjs rather than a delete, since nothing in the repo linked to it but the open web might.
- The ranked-queue page lives at **/queue**; `/live` is a permanent (308) redirect in next.config.mjs. Internals kept the old name on purpose — `lib/sync/live.ts`, the `live_ranked` table, the `bc-live-view` cookie — because the domain concept is still the live queue and renaming a table (or a cookie everyone already holds) to match a URL is churn with a migration attached
- Profile page = DB-first read-through (15-min fresh) with 429 fallback to stale cache; upsert only on `source === "api"`
- **Profile sub-views are `?tab=`, not routes**, and `ProfileSectionNav` (Ranked · Achievements · Gems) is how you move between them. Three sections of one page, so **nothing below the nav has a "back to profile"** — the header never moves, only the body swaps. `?tab=customize`, `legends` and `teams` are reached from inside Ranked and keep it lit rather than lighting nothing. `reachableTabs` is the guard: an unreachable value falls back to Ranked rather than rendering a hole. Lifetime legend/weapon records live *under* the gems that grade them, same section — a gem is the headline and the tables are the working, so sending someone to another page for the working would be a navigation step inside one thought. That it is a tab rather than a route is also what makes it free: the profile already fetches that exact GetPlayerStats payload for the header's weapon shares and legend titles, and the tab inherits the profile's crawler policy instead of needing a robots entry of its own

## External APIs

### Brawlhalla dev API (lib/brawlhalla-api.ts) — key: BRAWLHALLA_API_KEY
- Regions: `["ALL","BRZ","US-E","US-W","EU","SEA","AUS","JPN","SA","ME"]`; main three ladders US-E/EU/BRZ. **Japan disagrees with itself**: the leaderboard 400s on `region=JPS` but returns `region: "JPS"` in its rows. Canonical is `JPN` (the parameter form); `normalizeApiRegion` folds the reported spelling
- Modes: 1v1, 2v2, solo_2v2, 3v3 (3v3 is SOLO queue — single-player rows; ladder tops out Diamond, no Valhallans)
- **API never returns "Valhallan"** on `/ranked` — Diamond starts at 2000. The *leaderboard* does label it, and that label is the only source of truth: `getValhallanIds` (membership) + `getValhallanCutoff` → `isValhallan(rating, cutoff, wins)` (lib/tier.ts) as the fallback for players the id set doesn't cover. `TIER_FLOOR` has the static tier bands.
- **Valhallan is NOT a contiguous prefix of the ladder, and NOT a rating threshold.** Measured on US-E 1v1: rank 121 @ 2,507 is not Valhallan, rank 299 @ 2,138 is; the tier is interleaved all the way down and neither `rating` nor `best_rating` predicts it (it's the game's own top-N roster, and players keep the label after falling out). Consequences: (a) a walk that stops at the first non-Valhallan **page** misses 25-40% of the population — that bug shipped, and left real Valhallans rendering as Diamond on /live, the pro board and their own profile; (b) never set the cutoff to the true minimum rating — as `isValhallan`'s threshold it would promote every 2,138+ Diamond in the region. `cutoff.rating` is deliberately **the end of the unbroken run** (US-E ~2,508), which is both the honest "what do I need" answer and conservative as a fallback.
- Two walkers over `/v1/leaderboard/ranked`, different jobs, don't merge them: `discoverValhallanIds` (lib/sync/valhallan.ts) walks until a page holds **zero** Valhallans — complete but 6-8 pages/ladder, so it runs once a day in the sync-valhallan cron and persists to `valhallan_members`. `computeValhallanCutoff` (lib/sync/valhallan-cutoff.ts) walks only the unbroken prefix (1-3 pages) because it sits behind page renders. `getValhallanIds` unions both: daily-complete ∪ hourly-fresh, so either going cold shrinks the set rather than corrupting it.
- `max_results` caps at **50** (400s above it), so page depth is the only lever. `apiFetch` has no retry — a 429 mid-walk just ends it, which is why `discoverValhallanIds` returns a `complete` flag and the member write skips any ladder that came back short rather than overwriting a good row.
- **`/player/{id}/stats` reports wins per LEGEND, never per weapon**, and every legend wields two — so any per-weapon record is an attribution, not a reading. `lib/profile/lifetime-stats.ts` splits a legend's games/wins between its two weapons by time held (`timeheldweaponone`/`two`), which makes time held and share exact and the record an estimate; `/player/[id]/stats` says so above the table rather than in a footnote. Summing a legend's record into both weapons instead would double-count every match they ever played.
- **Lifetime totals are an order of magnitude above ranked ones** — "all modes" counts customs and unranked. Measured on five real accounts: 14.5k / 34.6k / 66k / 87.6k / 112k lifetime wins against season totals in the low thousands. Any threshold over lifetime numbers has to be sampled, not guessed; a first pass at 250-20,000 for the Total Wins gem put all five at the top level.
- **There is no account creation date anywhere in the API.** `/player/{id}/stats` is `level`, `xp`, `games`, `wins`, `clan`, `legends[]` and nothing else; the only date-shaped field in the whole surface is `clan_create_date`, which belongs to the clan. So "Brawlhalla account age" is not answerable — don't infer it from the ordinal of a `brawlhalla_id`, which would print a guess as a fact. Age-style achievements use `app_users.created_at` (Brawlchemist membership), and playtime proxies use `level` / lifetime `games`, which are real
- Tier strings carry division suffixes ("Gold 3") — strip via `toTier`

### brawltools esports API (lib/brawltools-api.ts) — keyless, "personal use only"
- `gameMode` is an INTEGER (1|2), unlike the dev API's strings
- `/v2/pr`: regions strictly NA/EU/SA/SEA/MENA, NO "ALL" (400); `playerId` is the ESPORTS id
- **`GET /v2/player/{playerId}` is the reverse bridge** esports id → `brawlhallaId` (nullable!); `/v2/player/bhId/{id}` goes the other way (404 = not a tracked competitor)
- `/v2/event`: `isOfficial=false` means INCLUDE community (returns everything) — there is NO community-only param, filter client-side; `nextToken` = startTime cursor; a year-mode is ~30–100 events (drain ≤4 pages)
- No per-tournament placements/details endpoint (placements are per-player only)

### Challengermode GraphQL (lib/challengermode-api.ts) — key: CHALLENGERMODE_REFRESH_KEY
- Auth: POST `/mk1/v1/auth/access_keys` {refreshKey} → a **20-minute** bearer (measured: minted 03:32, `expiresAt` 03:52 — it is not the hour this used to claim); single-flight memoized. Anything holding one token across a long job must refresh: a backfill that fetched once at startup failed its **last 17 tournaments consecutively** with "The current user is not authorized to access this resource", which reads like a permissions problem and is an expiry. Seventeen failures in a row at the tail of a run is the shape of a dead token, never of a private resource.
- Endpoint `https://publicapi.challengermode.com/graphql`; scalar is `UUID!` (not `Uuid!`)
- **brawltools event id == CM tournamentId for host "CM" events**. The SGG era is not on CM and it runs through **2024**, not 2021: measured by host, every official event from 2021-2024 is SGG (221 of them), CM first appears in 2025 (36 of 50) and takes over fully in 2026.
- `tournament(tournamentId:){ links { overviewUrl banner(size: MEDIUM){url} thumbnail(size: MEDIUM){url} } attendance { confirmedLineupCount } state }` — image fields REQUIRE the size arg
- POST isn't cached by Next fetch cache → wrap in `unstable_cache`; key must also be in Vercel project env

## Admin panel

- **Users leads, and it is a table.** It lists every account — the superset, since People is keyed by brawlhalla_id and an account that never claimed a player has no row there. The table is the *scan* (linked player, pro, flair, role, plan, joined) and carries no controls; `?edituser=` opens one card above it with the three forms, the same idiom People uses for `?edit=`. That split is what keeps a row one line high; the previous stack of cards was a paragraph per account with three forms in each. The flair column runs the site's own `resolveEarnedFlairs` against the cached profiles map rather than re-deriving entitlement, or the panel would drift from what the site actually renders.
- **The panel's cost is round trips, not queries.** Every statement here answers in 1–50ms; what an operator waits on is the trip to us-west-1 and back. So both list readers are ONE query each — `listAdminUsers` and `listAdminPeople` join `players` for the username/rating rather than making a second, sequential read for them. The old comment warning that joining `players` would drag the planner over `ranked_json` was wrong: **TOAST is only read when the column is**, and constraint #2 is about `SELECT *` and jsonb *expressions*, not about joining a table that owns a blob. Measured: `Index Scan using players_pkey`, 1.08ms for the whole Users statement. The one deliberate exception is the People region, which does read `ranked_json ->> 'region'` (49.7ms / 1,285 buffers for 171 rows) because the bare `ladder_region` column resolved for 0 of them.
- Container is `max-w-[1280px]`, matching every data page on the site. It was 960 while the panel was stacked cards, and that width clipped the Users table's last column.

## Known production problems

- **Abandoned database sessions, and what actually reaps them.** Serverless instances die mid-query and leave a backend holding a transaction and a Supavisor slot. Three were measured at 760s, 1,275s and 1,395s old on 2026-09-18, running `getPlayersByIds`- and profile-shaped queries. **The app holds no explicit transactions anywhere** (`grep -rn ".transaction("` is empty — every query is autocommit), so an open transaction with the client gone is *never* legitimate, which is what makes reaping them safe at any threshold. `ALTER ROLE postgres SET idle_in_transaction_session_timeout = '60s'` is applied and **it does NOT fix this** — measured, not suspected. A backend started at 15:02, after the change and therefore carrying the 60s setting, was found holding a transaction for 967s. The timeout never arms, because these sessions report `state = 'active'`, not `idle in transaction`: it is the extended-query signature of a client that sent Execute and never sent Sync, and Postgres only arms that timeout after a Sync. The setting is harmless and still covers true idle-in-transaction sessions, so it stays. **The remaining lever is a reaper we run ourselves** — `pg_terminate_backend` on any backend whose `xact_start` is older than a minute or two and whose `wait_event = 'ClientRead'`, which is safe precisely because the app holds no explicit transactions. Done by hand four times on 2026-09-18; it wants to be a cron. Query to check: `select pid, state, wait_event, now() - xact_start from pg_stat_activity where xact_start < now() - interval '90 seconds'`.
- **The top runtime error is `Vercel Runtime Timeout Error: Task timed out after 300 seconds`** — 803 occurrences / 322 users over seven days, on every route including `/`, `/player/[id]`, `/leaderboards/[mode]` and `/api/search/players`, going back to 2026-06-18. Nearly every other error cluster ("Failed query: …", caught and failed-open) is downstream of it. The pool config is already tight (`max: 4`, `idle_timeout: 20`, `fetch_types: false`), so the suspect is connection starvation rather than one slow query: serverless instances leave transactions open on `players` — `state = active`, `wait_event = ClientRead`, `xact_start` 30+ minutes old — holding both a lock and a Supavisor slot, and two of those were found and terminated by hand on 2026-09-18. `statement_timeout` cannot be set through :6543 (see lib/db/index.ts), so the lever would be `ALTER ROLE … SET statement_timeout` / `idle_in_transaction_session_timeout` on the database itself. **Not yet diagnosed or fixed** — do not assume a page that hangs is the feature you are working on.

## Design system

- Dark glass: cards `rounded-2xl border border-border/60 bg-card/50-60 backdrop-blur-sm`, rows `bg-card/40`
- Type: `font-display` headings; data is `font-mono tabular-nums`; micro-labels `font-mono text-[10px] uppercase tracking-wider text-muted-foreground`
- Tier colors: `text-tier-*` tokens + `TIER_TEXT_COLOR` map (components/site/primitives.tsx); positive/negative tokens for deltas, `warning` (amber) for caution and nothing else — gold is an accolade and negative is a loss, so borrowing either would have a "possible smurf" tag either congratulate the player or report an error. Every token is declared **twice**, in the light `:root` and again in `.dark`; the dark value is the one that ships. A token added to only one of them still resolves by inheritance, which is how it passes a glance and ships the wrong shade
- **`toTier` lives in `lib/tier.ts`, and there is one of it.** There were three private copies (leaderboard columns, podium, home Top Pros) and they had already drifted: the home card compared the whole tier string instead of the base word, so every "Gold 3" on it resolved to null and drew no helm at all. **`RankHelm` and `RankIcon` both take `tier: Tier | null` plus `rating` and own the fallback themselves** — never guard a call site with `{tier && ...}`, because that is exactly what renders nothing for the one label the ladder uses that isn't one of the seven. "Fallen Valhallan" (held the tier, off the roster) is that label: `RankIcon` draws the game's own Fallen emblem, `RankHelm` draws the **Diamond** helm, since no Fallen helm art exists and promoting them to Valhallan would claim a membership the ladder has taken back. Below the Diamond floor both derive from the rating, which is exact. **`LegendChip` has the same contract**: `legendId` is nullable and an unresolved one draws `/assets/legends/unknown.png`, so never guard a call site with `{slug && <LegendChip …>}` or an em dash. A missing main is not missing art — it is a player whose payload we have not read a legend out of yet — and a dash in a column of portraits reads as a broken cell. The *lists* (Best Picks, the podium's top legends) still render nothing when empty, because a short list is normal there and one unknown chip would claim they play one unknown legend
- `RankHelm` has art for **all seven tiers** — it used to be Valhallan + Diamond only, and several surfaces were written around that gap ("no helm below Diamond"). Derive the tier with `tierFromRating(rating, valhallan)`, never from rating alone: Valhallan is ladder membership. Helm art is 192px / ~10KB to match — `RankHelm` renders `unoptimized` like the rest of the codebase, so the raw file is what ships and a 1000px source would be 180KB per icon
- A player's identity renders the same everywhere: pro handle + `VerifiedMark` + `FlairMark`, never the raw Brawlhalla id. `FlairMark` takes the raw selection plus the `FlairContext` entitlement is derived from (accolades, developer role, manual grants — all assembled by `flairContextFrom` off the cached profiles map), not a resolved flair, so every surface runs one entitlement rule. It is a **client** component: the catalogue lives in Postgres and reaches the browser through `FlairCatalogueProvider`, mounted once in the root layout, because flair renders on both sides of the boundary — and that boundary was already paid for by `InfoTip`. Surfaces: profile, leaderboard rows/podium, home Live Rankings, /live, OTPs, power rankings, legends, both search dropdowns, /search, /favorites
- **The podium's art slot always fills.** A curated `profiles.favorite_skin` wins; failing that `placeholderSkinFor` (lib/skins.ts) picks one from the player's main legend, which costs nothing because `top_legend_id` is already denormalised onto the row.
